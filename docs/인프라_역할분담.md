# 인프라 역할 분담

## 운영 원칙

- 인프라 설정의 최종 책임자는 **인프라 총괄** 1명으로 한다.
- 세 명이 설정 파일을 동시에 수정하지 않는다.
- DB·AWS 담당자는 작업 결과를 별도 브랜치 또는 PR로 전달하고, 인프라 총괄이 최종 정합성을 확인해 병합한다.
- `.env`, AWS 키, DB 비밀번호, JWT Secret은 Git에 커밋하지 않는다.
- 공통 설정 변경 시 나머지 두 명에게 영향 범위와 필요한 환경변수를 공유한다.

## 담당자 1 — 인프라 총괄

### 지금 해야 할 일

- Spring Boot 애플리케이션용 `Dockerfile` 작성
- `docker-compose.yml`에 애플리케이션과 PostgreSQL 실행 구성
- `local`, `test`, `prod` 환경별 Spring Profile 분리
- 필요한 환경변수 목록과 `.env.example` 관리
- GitHub Actions CI 구성
  - Gradle 빌드
  - 테스트 실행
  - PostgreSQL 기반 Flyway 검증
- `/actuator/health`를 Docker 및 배포 헬스체크에 연결
- DB·AWS 담당자의 설정을 검토하고 최종 병합

### 배포처 결정 후

- Docker 이미지 빌드 및 레지스트리(ECR 또는 GHCR) 업로드
- `main` 브랜치 기준 CD 파이프라인 구성
- 배포 후 헬스체크 및 실패 시 이전 버전 복구 절차 구성
- Nginx 또는 ALB를 통한 HTTPS 연결
- 운영 CORS와 외부 공개 포트 제한

### 완료 기준

- 신규 개발자가 README만 보고 로컬 서버를 실행할 수 있다.
- PR마다 CI가 자동 실행되고 실패한 코드는 병합되지 않는다.
- 운영 배포가 한 가지 표준 절차로 재현된다.

## 담당자 2 — DB·마이그레이션

### 지금 해야 할 일

- PostgreSQL 16 기준으로 Flyway migration 전체 실행 확인
- H2 테스트와 PostgreSQL 간 문법·타입 차이 확인
- `TIMESTAMPTZ`, Identity PK, Unique/FK/Index 제약 검증
- 동네 등 개발용 초기 데이터 입력 방법 작성
- migration 파일 작성 규칙 정리
  - 적용된 migration 수정 금지
  - 신규 변경은 새로운 버전 파일로 추가
- PostgreSQL 통합 테스트 또는 Testcontainers 적용 검토
- CI에서 사용할 DB 생성 및 마이그레이션 검증 지원

### 배포처 결정 후

- 운영 DB 연결 설정 확인
- 자동 백업 또는 스냅샷 정책 설정
- 배포 전 migration 영향 확인 절차 작성
- migration 실패 시 복구 절차 작성
- 운영 DB 접근 권한 최소화

### 완료 기준

- 빈 PostgreSQL에서 모든 migration이 순서대로 성공한다.
- 주요 Repository 테스트가 실제 PostgreSQL에서 통과한다.
- 운영 DB 변경과 복구 방법이 문서화되어 있다.

## 담당자 3 — AWS·외부 스토리지

### 지금 해야 할 일

- S3 버킷 및 환경별 object key 규칙 정의
- Presigned PUT 업로드와 HEAD 검증 흐름 테스트
- MIME, 용량, 만료시간 및 미완료 파일 정리 정책 확인
- 로컬 S3 테스트 방식 결정
  - 실제 개발용 S3 버킷
  - 또는 LocalStack/MinIO
- 필요한 AWS 환경변수와 IAM 권한 목록 작성
- 하드코딩된 AWS 키가 없는지 확인

### 배포처 결정 후

- EC2/ECS 등에 IAM Role 연결
- S3 CORS 및 Bucket Policy 최소 권한 설정
- 로그 수집 환경 구성
- 업로드 실패·삭제 실패·만료 파일 정리 상태 확인
- CloudWatch 또는 선택한 로그 서비스에서 장애 확인 구성

### 완료 기준

- 로컬 또는 개발 환경에서 Presigned Upload가 정상 동작한다.
- 운영 서버는 정적 AWS Access Key 없이 S3에 접근한다.
- 버킷이 외부에 불필요하게 공개되지 않는다.

## 공동 확인 사항

- 인프라 변경 PR은 최소 한 명 이상 리뷰한다.
- 모든 환경변수는 `.env.example`과 README에 반영한다.
- 실제 비밀값은 GitHub Secrets 또는 서버 환경변수로만 관리한다.
- CI와 로컬에서 동일한 Gradle 명령을 사용한다.
- M1에서는 Docker, CI, PostgreSQL 검증, 기본 배포와 로그 확인까지 우선한다.
- M2 SimpleBroker WebSocket은 `replicas=1`을 전제로 한다. sticky session만으로 다중 인스턴스 라우팅 문제가 해결되지 않으며, 다중 replica 전환 전 외부 broker relay·Kafka·Redis 중 하나를 협의한다.
- staging, Terraform, 무중단 배포, 고급 모니터링은 M1 이후로 둔다.

## 권장 작업 순서

1. 인프라 총괄이 Dockerfile과 환경별 설정 구조를 확정한다.
2. DB 담당이 PostgreSQL/Flyway 통합 검증을 붙인다.
3. AWS 담당이 S3 개발 환경과 IAM 계약을 확정한다.
4. 인프라 총괄이 전체 내용을 GitHub Actions CI에 연결한다.
5. 배포처 확정 후 CD, HTTPS, 로그, 백업을 순서대로 적용한다.
