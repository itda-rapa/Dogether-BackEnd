## 2. 결정 추적

`D-번호`는 이 문서를 유일한 기준으로 사용한다. 다른 문서에서 같은 번호를 다른 의미로 재사용하지 않는다.

### D-18 HELPFUL 평판 범위 — 확정

- receiver는 Post/Comment 작성 시 저장된 `author_pet_id`다. receiver를 별도 컬럼으로 snapshot하지 않으며 작성자의 이후 Active Pet 변경은 과거 HELPFUL의 귀속을 바꾸지 않는다.
- `PetResponse.helpfulReceivedCount`는 HELPFUL만 합산한다. 삭제 target 자신의 row만 제외하고, 삭제 Post 아래 활성 Comment 및 삭제 parent 아래 활성 descendant는 유지한다. 부모 Post/Comment 상태, Block, reactor Pet의 이후 상태는 Comment aggregate의 제외 조건이 아니다.
- 차단은 신규 반응 접근을 404로 숨기지만 차단 전 row/평판을 제거하지 않는다. Post/Comment unsupported type은 `400 VALIDATION_FAILED`다.
- `GET /pets/{petId}/profile`은 기존 `PetResponse`와 분리된 공개 프로필 endpoint다. HELPFUL 집계 기준은
  그대로 재사용하며 `PetSearchItemResponse`·`PetDisplaySummary`를 확장하지 않는다.
- 10,500+ row·target 5 Pet·background 분산 fixture의 `EXPLAIN ANALYZE`에서 Post/Comment author Pet filter가 각각 약 10,000 rows를 제거했다. undeleted `(author_pet_id, id)` partial index는 Post `3.961ms → 1.789ms`, Comment `1.946ms → 1.341ms`로 scan 범위·buffer·cost를 줄였으므로 V33에 두 index를 추가한다. 이 판단은 이번 fixture 범위에 한정하며 모든 운영 데이터 분포를 보장하지 않는다.

### D-01 비로그인 공개 — 확정

- M3에서는 GUEST 방식을 포함한 비로그인 공개를 도입하지 않는다.
- 현재 로그인 사용자 기반 API와 Security 정책을 유지한다.

### D-02 OAuth 동일 이메일

- 자동 연결
- 기존 계정 본인 확인 후 명시적 연결
- 연결 거부

`users.email`이 대소문자 무시 UNIQUE이므로 별도 User 생성은 선택지에서 제외한다. 권장안은 이메일만으로 자동 연결하지 않고 기존 계정 인증 후 `/auth/oauth/link`로 연결하는 것이다. G1에서 callback→loginCode→exchange, 신규 사용자 `/auth/oauth/signup`, 기존 `AuthTokensResponse` 재사용 범위를 함께 확정한다.

### D-03 Pet 삭제 참조

Open Chat 참여와 과거 메시지·Meeting·Setlog/Post·Media를 삭제할지 표시만 비활성화할지 확정한다. 권장: 과거 기록은 유지하고 신규 행동만 차단한다. Friendship·Pending Request 정리는 회의 확정 요구사항이 아니므로 이 결정에 자동 포함하지 않는다.

### D-04 대댓글 깊이

**확정.** Root `depth=0`, 대댓글 `depth=1~3`을 허용하고 depth 4 생성은 `409 COMMENT_DEPTH_EXCEEDED`로 거절한다. Root 작성(`POST /posts/{postId}/comments`)과 대댓글 작성(`POST /comments/{parentCommentId}/replies`)은 분리하며, 두 요청 body는 strict `content`만 허용한다.

`GET /posts/{postId}/comments`는 flat all-row cursor를 폐기하는 breaking change다. `size`는 Root thread 수이고 cursor는 마지막 반환 Root의 `(createdAt, id)`다. `items`는 `replies`를 포함한 nested tree로 반환한다. Root 및 sibling은 `(createdAt, id)` 오름차순이고, 최종 visible Root candidate에 `size + 1`을 적용해 page를 계산한다.

soft delete는 행을 보존한다. 삭제 노드는 최종 visible active descendant를 잇는 경우에만 nullable tombstone으로 남고, 삭제 leaf는 숨긴다. 양방향 Block 노드는 subtree 전체를 숨기며 unblocked descendant를 승격하지 않는다. 대댓글 작성은 direct parent뿐 아니라 Root→parent 조상 모두의 Block을 검사한다. Parent/Post DELETE와 Reply CREATE 경합은 공유/쓰기 잠금 후 상태 재검증으로, 삭제가 먼저 확정되면 Reply CREATE가 404로 수렴한다.

### D-19 게시판 답변자 DIRECT 연결 — 확정

- API는 `POST /posts/{postId}/comments/{commentId}/direct-room`이며 request body는 없다.
- 대상은 해당 Post의 active Root Comment(`depth=0`) 작성 Pet이다. Reply는 제외한다.
- 호출자의 Active Pet은 Post author Pet 또는 대상 Comment author Pet 중 하나여야 한다. Pet ID를 외부 입력으로 받지 않는다.
- Post/Comment identity·visibility와 호출 권한은 Board가 담당한다. DIRECT pair 정규화·재사용·Participant 생성·동시성·Chat existence hiding은 Chat Core가 담당한다.
- same Pet·same-owner는 연결하지 않으며, 양방향 Block은 `CHAT_ROOM_NOT_FOUND` 404로 숨긴다.
- 삭제된 Post/Comment는 Board 경로에서 연결하지 않는다. 기존 room은 Chat 목록·상세 경로를 따른다.

### D-05 Chat 첨부 제한 — 확정

- 메시지당 `IMAGE` 또는 `VIDEO` 첨부는 1개다. IMAGE/VIDEO는 `body=null`, `mediaId`는 필수다.
- IMAGE는 `image/jpeg`, `image/png`, `image/webp`만 허용하고 최대 10 MiB다.
- VIDEO는 `video/mp4`만 허용하고 최대 50 MiB, 최대 5초다. 제품 문구의 짧은 영상 범위는 3~5초이며 계약 검증 상한은 5초다.
- 이번 배포는 `UPLOADED`와 `COMPLETED`를 모두 허용한다. 업로드 검증이 항상 `COMPLETED`로 전이된 뒤 별도 배포에서 `COMPLETED only`로 강화한다.
- `/api/v1/media/uploaded`는 단일·멀티파트 모두 완료 후 Object Storage `HEAD`의 실제 크기와 MIME을 init 선언값 및 D-05 정책과 대조한다. 불일치·빈 multipart는 `FAILED`로 전이하며, multipart는 abort하고 완료된 불일치 객체는 version 단위로 삭제를 시도한다. 검증 성공만 `COMPLETED`로 전이한다.
- DB/Kafka에는 `mediaId`만 저장한다. URL은 조회 시 재서명하고, 삭제·미완료 Media의 과거 메시지는 `mediaId`/`mediaType`을 유지하되 `contentType`, `fileSize`, `url`, `expiresAt`은 null로 반환한다.
- `INVALID_MEDIA_TYPE`은 HTTP 415, `MEDIA_SIZE_INVALID`는 HTTP 413을 HTTP/WS에서 동일한 code로 사용한다.
- `clientMessageId`는 방 단위 클라이언트 재전송 멱등 키이고, `eventId`는 서버가 발급하는 전역 Kafka/Outbox 이벤트 멱등 키다. 둘을 동일시하지 않는다.
- 실제 MP4 컨테이너 길이 판독은 업로드 검증 파이프라인에서 수행한다. `/api/v1/media/uploaded`는 VIDEO의 경우 실제 업로드된 객체의 `moov/mvhd`를 읽어 5초 상한을 검증하고, 초과 시 `MEDIA_DURATION_INVALID`(422)로 `FAILED` 전이한다. 클라이언트가 주장한 길이만으로 완료 상태를 판정하지 않는다.
- 현재 `/api/v1/media/init`은 purpose 구분 없이 IMAGE/VIDEO만 받는 공용 endpoint다. 따라서 D-05 MIME·크기 검증은 이 endpoint를 사용하는 모든 Media 초기화에 적용된다. 도메인별 제한이 달라지면 purpose를 추가해 정책을 분리한다.

- 전송 시 snapshot: 과거 맥락 유지, 삭제 후 노출 위험

권장: 현재값 참조, 접근 불가 시 preview 제거.

### D-08 Dashboard 집계 — 확정

- User는 `role=USER`, `accountStatus!=WITHDRAWN`이며 정지 계정은 포함한다.
- Pet은 논리 삭제를 제외한다. 정지 Pet·소유자는 포함하되, 소유 User가 `WITHDRAWN`이면 전체·기간 신규 모두 제외한다.
- Setlog는 `VISIBLE`, `isSeed=false`만 포함한다. 작성 Pet/User의 이후 삭제·탈퇴 상태는 기존 공개 콘텐츠 집계에 영향을 주지 않는다.
- BoardPost는 `PUBLISHED`·미삭제만 포함한다. 작성 Pet/User의 이후 삭제·탈퇴·정지 상태는 기존 게시글 집계에 영향을 주지 않는다.
- Report 생성 수는 요청 기간 내 생성된 모든 상태를 포함하고, `open`은 조회 시점의 현재 `OPEN` 수다. 최근 Report는 원문 없이 `reasonCode`만 반환한다.
- Risk의 `detectedUsers`는 요청 기간 내 `RiskSignal`이 하나 이상 발생한 고유 `actorUserId` 수다. `actorUserId`는 위험 행동 주체, `targetUserId`는 상대방이며 SafetyCase subject와 혼용하지 않는다.
- 모든 지원 `RiskSignalType`을 `signalsByType`에 반환하고, 기간 내 0건인 유형은 값 `0`으로 명시한다. 새 enum 추가 시 계약 테스트와 Front 표시 항목을 함께 갱신한다.
- Safety open case는 조회 시점의 `OPEN`, `REVIEWING` 합계다.
- Storage backlog는 조회 시점의 `PENDING`, `RETRY`, `FAILED`를 노출한다. `FAILED`는 해결되지 않은 운영 항목이지만 자동 재처리 `RETRY`와 합산하지 않고 별도 수치로 유지한다.
- 최근 Report·SafetyCase는 요청 기간과 무관한 전체 최신 10건이다.
- 모든 기간형 수치는 KST `[from 00:00, to 다음 날 00:00)`의 생성·발생 기준이며, 현재 상태·최근 목록 지표와 의도적으로 구분한다.
- Pet도 다른 콘텐츠와 동일하게 `total`, `newInPeriod`를 제공한다.

AI/Open Chat에서 특정 상대방이 없는 방·메시지 단위 Risk 신호를 추가하기 전에는 임의의 `targetUserId`를 사용하지 않는다. 공용 Risk 계약의 `targetUserId` nullable 여부 또는 별도 대상 모델을 먼저 확정한다.

### D-09 반복 접촉 임계값

권고 초안: 동일 대상에게 30일 내 거절 후 재접촉 3회 이상이며 최소 2개 날짜. 점수·감쇠·Case unique 범위는 fixture로 검증 후 확정.

### D-10 위치·코드

- 약속 ±1시간
- 제출 간 5분
- 거리 100m
- accuracy 50m 미만
- 코드 4자리, 5분, 5회, 재발급 시 이전 폐기

Location 계약에서 좌표 범위 밖·비수·음수 accuracy·허용 미래 시각 초과는 `LOCATION_INVALID`, 수집 허용 시간보다 오래된 위치는 `LOCATION_STALE`다. 50m 이상인 유효 accuracy는 오류가 아니라 `LOW_ACCURACY`로 분류해 Meeting의 확인 코드 fallback으로 넘긴다. 거리 utility는 계산만 하고 100m 정책과 양쪽 제출 5분 정책은 Meeting이 판정한다.

위 값은 권고 기본값이며 모바일 실측 후 확정한다.

측정 결과와 적용/미적용 근거를 남긴다. 적용한 경우에만 Cache TTL·무효화 또는 Lock 실패 정책과 테스트를 요구한다.

### D-15 ELK·로깅 범위

### D-16 산책 경로 완료선

저장·조회 필수 범위와 안내·AI 가중치의 포함 여부, fallback을 이정수·AI 담당이 확정한다.

### D-17 Pet 프로필 이미지 동시성

**확정.** PUT/DELETE 모두 `If-Match`로 현재 Pet `version`을 전달하는 명시적 낙관적
잠금 정책을 사용한다. 값은 큰따옴표로 감싼 0 이상의 10진수 하나(예: `"3"`)이며,
누락·malformed·반복 헤더는 `400 VALIDATION_FAILED`, stale version은
`409 CONCURRENT_UPDATE_CONFLICT`다.

PUT body는 양의 `mediaId`만 허용하고, 요청자 소유의 IMAGE이며 `UPLOADED` 또는
`COMPLETED`인 Media만 연결한다. Media 검증은 같은 Media를 재지정하는 PUT no-op에서도
생략하지 않는다. 실제 link 교체/제거만 Pet `version`을 1 증가시킨다. 같은 Media PUT은
요청 Media를 조회·검증한 뒤 no-op으로 처리하며 version을 유지한다. 이미 비어 있는 DELETE는
별도의 `MediaRepository` command lookup 및 Media 소유권/type/status validation 없이 Pet profile
link 기준 no-op으로 처리하며 version을 유지한다. DELETE는 body·response body·ETag가 없다.

두 API는 Pet의 `profile_asset_id` link만 변경한다. 기존 Media row와 `deletedAt`, S3
객체 및 `StorageDeleteJob` lifecycle은 변경하지 않으며, Media 물리 삭제 정책은 별도
결정사항으로 남긴다.

### D-19 Pet 공개 프로필 가시성 — 확정

- `GET /pets/{petId}/profile`은 인증된 조회자만 사용한다. 대상 Pet은 `ACTIVE`·미삭제이고 소유자 계정도
  `ACTIVE`여야 한다. Pet 부재, 공개 불가 상태, 어느 방향이든 조회자와 소유자 사이의 Block은 모두
  `404 PET_NOT_FOUND`로 existence hiding 한다. 신규 오류 코드는 만들지 않는다.
- 자기 Pet은 조회 가능하지만 `relationship=null`이다. 비자기 대상도 조회자의 Active Pet이 없으면 성공하고
  `relationship=null`이다. Active Pet이 있는 비자기 대상만 기존 FriendRelationship 값을 계산한다.
- 공개 응답은 `PetPublicProfileResponse`의 14개 필드만 사용한다. `ownerUserId`, `ownerPublicTag`,
  `weightKg`, `careNote`, `status`, `deletedAt`, `verifiedAt`, `active`, `version`은 반환하지 않는다.
