# 같이놀개 M3 상태 전이

## 1. OAuthLoginCode

```text
ISSUED → CONSUMED
ISSUED → EXPIRED
```

- code는 짧은 수명·1회용이다.
- CONSUMED code 재사용은 `410 OAUTH_LOGIN_CODE_CONSUMED`, logical expiry 뒤 cleanup grace 안의 code는 `410 OAUTH_LOGIN_CODE_EXPIRED`다. 약 1분 grace 뒤 physical delete된 code는 `401 OAUTH_LOGIN_CODE_INVALID`다.
- signupToken도 동일하게 logical expiry 뒤 grace 안에는 `410 OAUTH_SIGNUP_TOKEN_EXPIRED`, physical delete 뒤에는 `401 OAUTH_SIGNUP_TOKEN_INVALID`다. 두 artifact의 transient verified email snapshot은 TTL + cleanup grace 동안 DB row에 남을 수 있다.

신규 OAuth 사용자:

```text
LOGIN_CODE EXCHANGED → SIGNUP_REQUIRED → PROFILE_COMPLETED → TOKEN_ISSUED
                                  └────→ SIGNUP_TOKEN_EXPIRED
```

## 2. Pet

```text
ACTIVE ────→ DELETED
SUSPENDED ─→ DELETED
```

- 여기서 `ACTIVE`는 `PetStatus` 값이다. 사용자의 현재 대표 반려견(`user.active_pet_id`)이면 대체 Pet 선택 전 삭제를 거절한다.
- `DELETED ↔ deleted_at IS NOT NULL`.

## 3. Media

```text
INIT → UPLOADED → COMPLETED
  └──────┴──────→ FAILED

StorageDeleteJob:
PENDING → PROCESSING → COMPLETED
             └──────→ RETRY → PROCESSING
             └──────→ FAILED
```

- `UPLOADING`은 클라이언트 전송 상태이며 서버의 `MediaStatus`에는 저장하지 않는다.
- Chat 첨부는 UPLOADED/COMPLETED만 가능하다.
- 물리 삭제 진행 상태는 Media가 아니라 `StorageDeleteJobStatus`로 관리한다.
- 신고 Evidence 보존 대상은 정책 확정 전 물리 삭제 금지.
- Pet 프로필 이미지 POST/PUT는 위 Media 상태를 검증한 뒤 Pet의 link를 설정·교체한다. DELETE는 별도의
  MediaRepository command lookup 및 Media 소유권/type/status validation 없이 Pet의 link만 해제한다. 세 요청 모두 Media row, `deletedAt`, S3 객체 또는
  `StorageDeleteJob`을 생성·변경하지 않는다.

## 4. ChatMessage

```text
CLIENT SEND
  → 권한·typed payload·원본 검증
  → STORED
  → DIRECT realtime 또는 Kafka PUBLISHED
  → DELIVERED
```

- 같은 `clientMessageId`는 기존 메시지를 반환한다.
- 사용자 전송 메시지(`TEXT`, `IMAGE`, `VIDEO`, `SETLOG_SHARE`)는 모두 `clientMessageId`가 필요하다.
- TEXT는 body, IMAGE/VIDEO는 attachment만 허용하며 body는 반드시 `null`이고 caption은 지원하지 않는다. SETLOG_SHARE는 setlog만 허용한다.
- AI 분석은 STORED/DELIVERED 뒤 별도 분기이며 전달 상태를 바꾸지 않는다.

## 5. MeetingVerification·Meeting

영속 상태(`meeting_verifications.status`):

```text
SUBMITTED(raw 보관)
  ├→ ACCEPTED(raw scrub)  — GPS 확정
  └→ EXPIRED(raw scrub)   — meetAt + window 경과
SUBMITTED → CODE_REQUIRED(raw scrub)  — 같은 Pet 의 LOW_ACCURACY 재제출
CODE_REQUIRED → (상대 verify → issuer confirm) ACCEPTED — CODE Meeting 확정
CODE_REQUIRED ─ GPS 재제출 불가(새 clientRequestId 는 409 MEETING_VERIFICATION_CODE_REQUIRED)
```

사용자용 API 상태(`MeetingVerificationApiStatus`):

```text
NOT_SUBMITTED
  → WAITING_COUNTERPART
  → GPS_CONFIRMED
  → CODE_REQUIRED → CODE_CONFIRMED
  → REJECTED / EXPIRED
```

- 첫 ACCEPTABLE 제출은 `SUBMITTED`(raw 보관) + API `WAITING_COUNTERPART`.
- LOW_ACCURACY 제출은 `CODE_REQUIRED`(raw 즉시 scrub) + API `CODE_REQUIRED`.
- LOW_ACCURACY 로 `CODE_REQUIRED` 가 된 Pet 은 새 `clientRequestId` GPS 로 `SUBMITTED`/`CODE_REQUIRED` 를 갱신할 수 없다(`409 MEETING_VERIFICATION_CODE_REQUIRED`). 이후 확정 경로는 Confirmation Code 흐름(#149)만 사용한다.
- 같은 `clientRequestId` 재시도는 서버 수신 deadline 보다 먼저 ledger 를 조회해 replay/conflict 로 수렴하므로, deadline 경과 뒤에도 기존 결과(확정/대기/`CODE_REQUIRED`)를 그대로 반환한다. 단, Meeting 이 없을 때는 현재 최신 verification 의 terminal/`CODE_REQUIRED` 상태가 과거 ledger 최초 상태보다 우선해, 만료 worker 가 `EXPIRED` 로 전이했거나 `CODE_REQUIRED` 로 전이된 뒤에는 동일 요청 replay 도 각각 `EXPIRED`/`CODE_REQUIRED` 로 수렴한다.
- 두 제출이 모두 `SUBMITTED`이고 약속 시간창·양쪽 `submittedAt` 간격·거리를 만족하면 양쪽을 `ACCEPTED`(raw scrub)로 전이하고 GPS Meeting 을 1건 생성한다.
- `meetAt + meetingTimeWindow` 경과 뒤 아직 GPS 확정되지 않은 `SUBMITTED` 는 `EXPIRED`(raw scrub)로 전이한다.
- 확정 Meeting 이 있는 카드는 수동 취소를 금지하고, Block 자동 정리도 확정 카드는 취소하지 않는다.
- `LocationService`가 평가한 `LOW_ACCURACY`만 CODE_REQUIRED이다. `LOCATION_INVALID`와
  `LOCATION_STALE`은 위치 제출 오류이며 CODE fallback으로 전이하지 않는다.
- CODE_REQUIRED에서는 참여 Pet이 코드를 발급하고, 상대 Pet의 verify 뒤 코드 생성자가
  confirm해야만 CODE Meeting이 생성된다. verify만으로는 확정되지 않는다.
- 기존 Code cycle이 있으면 최초 issuer만 만료·무효화 후 재발급할 수 있고
  `issuerPetId`는 유지된다. 다른 참여자의 재발급은 403이다.
- 새 Code mutation은 `receivedAt < meetAt + meetingTimeWindow`일 때만 가능하다.
  종료 시각 정확한 경계부터 409이며, 이미 확정된 CODE Meeting 재조회는 기존 결과를 유지한다.
- 카드 취소·시간 만료 후 제출은 거절.

## 6. Review·Footprint

```text
MEETING_CONFIRMED
  ├→ REVIEW_SKIPPED
  └→ REVIEW_SUBMITTED → FOOTPRINT_GRANTED 또는 FOOTPRINT_DUPLICATE_DAY
```

- Review는 Pet당 Meeting 1회.
- Footprint는 후기 제출자에게만 지급.

## 7. RiskSignal·SafetyCase

```text
Outbox Relay:
PENDING → PROCESSING → SENT
              ├─────→ RETRY → PROCESSING
              └─────→ FAILED

lease 만료 PROCESSING → 새 claimToken으로 PROCESSING 재선점

EVENT RECEIVED
  → DUPLICATE_IGNORED
  → RECORDED → BELOW_THRESHOLD
             → CASE_OPEN

OPEN → REVIEWING
OPEN/REVIEWING → DISMISSED
               → WARNING_RECORDED
```

- Relay는 at-least-once이며 Kafka ack 후 `SENT` 저장 실패 시 같은 `eventId`가 재발행될 수 있다.
- 이전 Worker의 상태 변경은 `claimToken` fencing으로 거부하고 Consumer는 `eventId`로 중복을 제거한다.
- 신규 Case는 임계값 이상일 때만 열고, 이미 열린 Case는 rolling window 점수가 임계값 아래로 내려가도 최신 snapshot으로 갱신한다.
- 관리자 API는 `OPEN`에서 바로 종료하거나 `REVIEWING`을 거쳐 종료할 수 있다.
- Case action은 append-only 감사 이력을 남긴다.
- 자동 SUSPENDED 전이는 M3 범위가 아니다.

## 8. AI Moderation

```text
MESSAGE_DELIVERED
  → RULE_NOT_MATCHED
  → RULE_MATCHED → AI_PENDING
                 → AI_SCORED → RISK_SIGNAL
                 → AI_FAILED/TIMEOUT
```

- FAILED/TIMEOUT은 메시지 전달을 되돌리지 않는다.
- Retry 횟수 소진 후 DLQ 또는 기록만 수행한다.

## 9. WalkSession

```text
RECORDING → COMPLETED
RECORDING → CANCELED
RECORDING → EXPIRED
```

- RECORDING에서만 points를 추가한다.
- 같은 sequence/clientBatchId 재전송은 멱등 처리한다.
- COMPLETED 뒤 서버가 거리·시간을 확정한다.

## 10. Board Comment

```text
ACTIVE --PATCH--> ACTIVE
ACTIVE --DELETE--> DELETED
```

- Root는 `parentCommentId=null`, `rootCommentId=null`, `depth=0`이다. 대댓글은 직접 parent·Root를 갖고 `depth=1~3`이며 depth 4 생성은 `409 COMMENT_DEPTH_EXCEEDED`다.
- `DELETED`는 soft delete(`deleted_at` 설정)이며 물리 삭제나 자식 승격 전이는 없다. 활성 자손까지 연결하는 deleted ancestor는 tombstone, 활성 자손이 없는 deleted leaf는 hidden이다. tombstone의 `authorPet`, `content`, `version`, `createdAt`, `updatedAt`, `helpfulCount`, `helpfulByMe`는 모두 null이다.
- 차단 작성자 노드는 그 자손 subtree와 함께 hidden이다. deleted tombstone으로 바꾸거나 차단되지 않은 자손을 승격하지 않는다.
- 목록은 Root thread cursor pagination이다. `size`는 Root 수이고, candidate의 visibility·tombstone 필요 여부를 `LIMIT size + 1` 전에 확정한다. Root 및 sibling 정렬은 `(createdAt, id)` 오름차순이다.
- 대댓글 작성은 User·Active Pet을 잠근 뒤 게시글 공유 잠금, 활성 부모 공유 잠금을 획득해 조상 경로·차단·depth를 재검증한다. 부모 DELETE 또는 게시글 DELETE가 먼저 쓰기 잠금을 획득한 경우 대기한 대댓글 작성은 재검증 후 404로 수렴한다.

## 11. HELPFUL 반응·평판

```text
ABSENT --PUT HELPFUL--> PRESENT
PRESENT --PUT HELPFUL--> PRESENT
PRESENT --DELETE HELPFUL--> ABSENT
ABSENT --DELETE HELPFUL--> ABSENT
```

- Post는 LIKE와 HELPFUL을, Comment/Reply는 HELPFUL만 지원한다. actor는 현재 Active Pet이고 self 금지는 User 기준이다.
- Post/Comment target delete는 soft delete다. Reaction row는 보존되지만 target 자신의 deleted_at 이후에는 해당 target의 HELPFUL만 receiver aggregate에서 제외된다. 삭제된 Post 아래의 활성 Comment와 삭제된 parent 아래의 활성 descendant는 계속 합산된다.
- Block 또는 reactor Pet의 이후 상태 변경은 과거 HELPFUL row/receiver 평판을 변경하지 않는다. 다만 신규 반응은 visibility·block 확인 뒤 404 hiding을 적용한다.

## 12. MeetingSuggestionScan

```text
PENDING ─→ PROCESSING ─→ COMPLETED
                  └───→ FAILED_RETRYABLE ─→ PROCESSING (next_retry_at 이후 재claim)
                  └───→ FAILED_FINAL
PROCESSING (lease 만료) ─→ PROCESSING (새 claim holder, claimToken 교체)
```

- 매일 07:00 Asia/Seoul 에 전날(00:00~24:00 KST) DIRECT 방 Scan 이 생성된다. 생성은 (room_id, source_date) 멱등이며 retry worker 는 새 Scan 을 만들지 않는다.
- claim 은 `FOR UPDATE SKIP LOCKED` + claimToken fencing(RiskSignal Outbox 패턴). 상태 확정은 현재 claimToken 소유권 검증으로 stale worker 를 차단한다.
- retry 는 Scan 에 저장된 referenceDate 를 재계산하지 않는다(최초 생성 값 유지).
- AI 422(INVALID_REQUEST) 는 재시도해도 같은 응답이므로 FAILED_FINAL. TIMEOUT·MODEL_ERROR 는 FAILED_RETRYABLE, maxAttempts 초과는 FAILED_FINAL.
- Suggestion 저장도 Scan 이 `PROCESSING + 현재 worker claimToken` 일 때만 가능하다. 짧은 트랜잭션에서 Scan 행을 `FOR UPDATE` 로 잠근 뒤 소유권을 검증하고 후보를 저장한다.
