# 같이놀개 M3 제품 정책

> 기준: M2 실제 구현 + 2026-08-20 백엔드 회의  
> M2 문서의 계획 중 현재 미구현인 항목은 M3 신규 범위로 재분류한다.

## 1. 마일스톤

### M3 신규·확장

- 만남 위치 확인, 확인 코드, 후기, 발자국
- 채팅 이미지·영상 첨부와 Setlog 공유
- 관리자 Dashboard 실제 통계
- 거절 후 반복 접촉 RiskSignal과 관리자 검토
- Pet 삭제, Google·Naver OAuth, 게시글 도움 표시
- 대댓글, 게시글 Place, 이미지 수정·삭제
- Open Chat AI 검열과 typed media event
- Place·지도 검색·GPS·산책 경로

### M2 보완

- 기존 Admin 신고 구현 기준선·테스트 정리
- DIRECT/Open Chat 계약과 권한 재점검
- Pet·Board·Setlog·Chat Media N+1 제거
- Setlog Reaction lock 경합 측정·보완
- StorageDeleteWorker 실제 S3 삭제·retry·lease 검증
- Flyway·Kafka·WebSocket·S3·Hikari 운영 설정

### 이번 명세에서 제외

- 메시지 수정·삭제·읽음 표시
- 자동 AI 제재
- iOS/Android 앱 포팅
- 예약 시스템
- 결제·포인트·발자국 순위
- Redis·ELK의 목적 없는 전면 도입

## 2. 공통 권한

- 기본 정책은 로그인 사용자만 서비스 API를 사용한다.
- `ADMIN`, `SUPER_ADMIN`만 `/admin/**`에 접근한다.
- Chat SEND/조회는 방 참여자만 가능하고 차단·나가기 정책을 적용한다.
- Pet·Media·Setlog 변경은 소유자만 가능하다.
- M3에서는 비로그인 공개를 도입하지 않고 현재 로그인 기반 접근 정책을 유지한다.

## 3. OAuth

- 현재 runtime Provider는 `GOOGLE`만 지원한다. `NAVER`는 공통 enum·DB CHECK에만 남아 있으며 adapter, endpoint, 설정, 연동은 없다.
- OAuth 가입은 별도 이메일 인증을 요구하지 않는다.
- 브라우저 전용 시작·callback은 각각 `GET /oauth2/authorization/google`, `GET /login/oauth2/code/google`이며 JSON API가 아니라 `302 Found` redirect 계약이다. 활성화하지 않으면 두 endpoint는 `404`다.
- Google Authorization Code + OIDC 흐름은 scope `openid email`, `state`, PKCE S256, nonce를 사용한다. state·verifier·nonce는 Redis에 일회용으로 보관하고, ID Token의 issuer·nonce·`email_verified=true`를 검증한다. OIDC 구조상 복수 audience가 가능해도 Dogether는 configured client ID 하나만 audience로 신뢰하며 추가 audience가 있으면 실패시킨다. `azp`는 모든 ID Token의 필수 claim이 아니며, 제공되면 configured client ID와 일치해야 한다. `sub`를 providerSubject/identity key로 사용하고 email은 identity key로 사용하지 않는다.
- callback은 email 존재와 `email_verified=true`를 요구한다. Gmail, Workspace, `hd` 여부로 추가 제한하지 않으므로 `hd` 없는 third-party verified email도 허용한다.
- Provider callback에서 사용자를 식별한 뒤 5분 수명의 1회용 `loginCode`를 발급하고 허용 목록의 Front success callback URL로 `?loginCode={code}&provider=GOOGLE`를 붙여 Redirect한다. 실패도 허용 목록의 error callback URL로 `?errorCode={allowlisted-code}`만 붙여 Redirect한다. 허용 errorCode는 `INTERNAL_ERROR`, `OAUTH_STATE_INVALID`, `OAUTH_STATE_EXPIRED`, `OAUTH_AUTHORIZATION_DENIED`, `OAUTH_IDENTITY_VERIFICATION_FAILED`, `OAUTH_PROVIDER_UNAVAILABLE`이며 Location에는 JWT, provider token, email, providerSubject, raw provider response를 포함하지 않는다.
- 기존 OAuth 연결 사용자는 `loginCode` 교환 후 기존 `AuthTokensResponse`와 같은 JWT 응답을 받는다.
- 신규 사용자는 교환 응답의 10분 수명 `signupToken`으로 trim 후 2~20자 nickname·neighborhoodCode를 제출한 뒤 가입을 완료하고 JWT를 받는다.
- 기존 동일 이메일 계정은 DB UNIQUE 정책상 별도 User로 만들지 않으며 자동 연결·연결 endpoint도 제공하지 않는다. 이는 최종 account-link 정책이 아닌 현재 안전 경계이며, 교환은 `409 OAUTH_ACCOUNT_LINK_DECISION_REQUIRED`로 종료하고 loginCode를 소비하지 않는다. 교환 뒤 가입 중 발생한 late email UNIQUE race는 signup transaction 전체를 rollback하고 `409 CONCURRENT_UPDATE_CONFLICT`로 종료하며, 기존 loginCode를 복원하거나 signupToken을 link context로 재해석하지 않는다.
- Google access/refresh token 및 ID token 원문은 영구 저장하거나 클라이언트에 반환하지 않는다.

## 4. Pet 삭제

- 삭제는 Soft Delete다.
- Active Pet은 다른 Pet을 먼저 활성화하지 않으면 삭제할 수 없다.
- 삭제 Pet은 신규 상호작용·채팅 SEND·약속 생성에 사용할 수 없다.
- 과거 메시지·약속·후기·발자국은 감사·기록 목적으로 유지하되 표시 정책을 적용한다.
- Open Chat 참여 기록과 과거 데이터의 보존·표시 방식은 `D-03`에서 확정한다.
- Friendship·Pending Request 정리는 회의 확정 요구사항이 아니며 별도 영향도 검토 없이 삭제 범위에 포함하지 않는다.

## 5. 게시판·HELPFUL 평판

- 게시글은 `LIKE`, `HELPFUL`을 지원하고, 댓글·대댓글 반응은 `HELPFUL`만 지원한다. 각 반응의 식별은 `reactorPet + target + reactionType`이며 `PUT`/`DELETE`는 멱등이고 포인트·발자국·보상과 연결하지 않는다.
- actor는 요청 시점의 Active Pet이다. 자기 반응은 Pet이 아니라 User 기준으로 금지하므로 Active Pet을 바꿔도 자신의 게시글·댓글에는 반응할 수 없다. 수신 Pet은 콘텐츠 작성 시 저장된 `author_pet_id`이며 이후 Active Pet 변경으로 바뀌지 않는다.
- 기존 `reactionCount`·`reactedByMe`는 LIKE 의미를 유지하고, HELPFUL은 `helpfulCount`·`helpfulByMe`로 분리한다. 댓글 tree의 활성 노드는 HELPFUL 필드를 non-null로, tombstone은 null로 반환한다.
- HELPFUL만 Pet `helpfulReceivedCount`에 합산한다. 삭제된 게시글/댓글 자신의 HELPFUL만 제외하며 row를 물리 삭제하지 않는다. 삭제된 게시글 아래의 활성 댓글 및 삭제된 부모 댓글 아래의 활성 자손 댓글 HELPFUL은 계속 합산한다. 차단과 반응 Pet의 이후 suspended/deleted 상태는 기존 row·평판을 소급 제거하지 않는다.
- 게시글이 차단·비공개이면 반응 요청은 `404 BOARD_POST_NOT_FOUND`로 은닉한다. 댓글 target 또는 Root→target 조상 작성자와 차단이면 `404 BOARD_POST_COMMENT_NOT_FOUND`, 부모 게시글과 차단이면 `404 BOARD_POST_NOT_FOUND`다. 지원하지 않는 Post/Comment 반응 타입은 `400 VALIDATION_FAILED`다.
- `GET /pets/{petId}/profile`은 로그인 사용자에게만 공개 Pet 프로필을 제공한다. `ACTIVE`·미삭제 Pet과 `ACTIVE` 소유자만 대상이며, 조회자와 소유자 사이의 양방향 Block 및 공개 불가 대상은 모두 `PET_NOT_FOUND`로 은닉한다. 자기 Pet 또는 조회자의 Active Pet이 없으면 `relationship`은 `null`이다. 기존 `PetSearchItemResponse`·`PetDisplaySummary`는 확장하지 않는다.
- 댓글은 Root `depth=0`부터 대댓글 `depth=1~3`까지 허용한다. Root 작성과 대댓글 작성은 별도 API이며, 요청 본문은 모두 `content`만 허용한다.
- 댓글 목록은 flat 목록을 폐기하고 Root thread 단위의 중첩 트리로 반환한다. cursor와 `size`는 Root thread의 불변 `(createdAt, id)` 순서를 기준으로 한다.
- 댓글 soft delete는 행을 보존한다. 삭제 노드에 최종적으로 보이는 활성 자손이 있으면 최소 식별자와 `replies`만 남긴 tombstone으로 반환하며, 삭제 leaf는 반환하지 않는다.
- 조회자와 작성자 사이 양방향 차단 관계가 있는 댓글은 그 자손까지 숨긴다. 숨긴 자손을 상위로 승격하지 않는다. 대댓글 작성도 Root부터 부모까지의 모든 조상 차단 관계를 검사한다.
- 부모 댓글 삭제 및 게시글 삭제와 대댓글 작성이 경합할 때, 공유 잠금과 삭제 쓰기 잠금으로 대기한 요청은 잠금 획득 뒤 활성 부모·공개 게시글 상태를 다시 검증한다.
- 게시글의 직접 작성 Root 댓글 작성자 Pet만 게시글 작성자 Pet과 DIRECT 연결 대상이다. Reply는 대상에서 제외한다.
- 호출자의 Active Pet은 게시글 작성 Pet 또는 대상 Root 댓글 작성 Pet 중 하나여야 하며, 제3자 Pet은 연결을 시작할 수 없다.
- same Pet과 same-owner Pet은 연결하지 않는다. 양방향 Block은 기존 Chat의 `CHAT_ROOM_NOT_FOUND`(404) existence hiding으로 수렴한다.
- 삭제된 Post 또는 Comment는 Board 경로에서 DIRECT 연결에 사용할 수 없다. 기존 Chat room은 Chat 목록·상세 경로에서만 접근한다.
- 게시글은 선택적으로 내부 `placeId`를 참조한다.
- Pet 프로필 이미지 POST/PUT는 기존 Media 소유권·상태 검증을 재사용한다. DELETE는 별도의 MediaRepository command lookup 및 Media 소유권/type/status validation 없이 Pet의 Media link만 해제한다. 세 API 모두 Media row·`deletedAt`·S3 객체·`StorageDeleteJob`은 변경하지 않는다.

## 6. Media와 채팅

- 지원 사용자 전송 타입은 `TEXT`, `IMAGE`, `VIDEO`, `SETLOG_SHARE`다.
- `CARD`, `SYSTEM`은 서버 생성 전용이다.
- IMAGE/VIDEO는 업로드 완료된 발신자 소유 Media만 참조하며, 하나의 Media는 한 Chat 메시지에만 첨부할 수 있다(재사용 금지).
- IMAGE/VIDEO 메시지는 `body`를 사용하지 않으며 반드시 `null`이다. 별도 caption은 지원하지 않는다.
- Presigned URL은 응답 시 발급하며 DB에 저장하지 않는다.
- SETLOG_SHARE는 `setlogId`를 저장하고 조회 시 현재 접근 가능한 요약을 반환한다.
- SETLOG_SHARE는 발신자(Active Pet 소유 User)가 작성한 Setlog만 공유할 수 있다(내 것만 공유).
- 삭제·차단·비공개 Setlog는 원문 preview 대신 접근 불가 상태를 반환한다.
- 신고 Evidence가 있는 첨부의 삭제·보존은 `D-06` 결정 전 자동 삭제하지 않는다.

## 7. 관리자 Dashboard

- 기본 기간은 오늘을 포함한 최근 7일, 최대 90일이다.
- 한국 날짜 경계를 UTC `Instant` 범위로 변환한다.
- User, Pet, Setlog, BoardPost, Report, SafetyCase 통계를 제공한다.
- 최근 신고·검토는 최대 10건이다.
- 목록에 대화 원문·이메일·토큰을 포함하지 않는다.
- User는 일반 사용자 중 탈퇴 계정을 제외하고, Pet은 논리 삭제를 제외하며 정지 상태는 포함한다.
- Setlog는 공개·비 Seed, BoardPost는 공개·미삭제 데이터만 집계한다.
- 기간형 Report·Risk 지표와 현재 backlog형 Safety·Storage 지표를 구분한다.
- 최근 신고·검토는 기간과 무관한 전체 최신 항목이며 결정적 보조 정렬을 적용한다.

## 8. 위험 신호와 AI

- Greeting 무응답, Friend reject, Block, Chat leave/재접촉, AI 위험 결과를 RiskSignal로 정규화한다.
- `eventId`는 전역 유일하며 중복 event는 점수를 다시 올리지 않는다.
- 거절 후 반복 접촉 1번은 규칙으로 처리한다.
- AI 검열은 비동기이며 정상 채팅 전달을 막지 않는다.
- 임계값 초과 시에만 SafetyCase를 열고 자동 제재하지 않는다.
- RiskSignal에는 메시지 원문을 복제하지 않는다.
- 관리자의 Evidence 원문 조회는 감사 로그를 남긴다.

## 9. Location·Meeting

- 위치 입력은 WGS84 `latitude`, `longitude`, `accuracyMeters`, `capturedAt`이다.
- 좌표·stale·accuracy 검증은 Location 영역, 약속 참여·시간·거리·양쪽 확인은 Meeting 영역이 담당한다.
- 권고 기본값은 약속 ±1시간, 양쪽 제출 간 5분, 거리 100m, accuracy 50m 미만이다.
- accuracy 기준을 충족하지 못하면 4자리 확인 코드로 전환한다.
- 후기 제출은 선택이고 발자국은 후기 제출 시 적립한다.
- 동일 상대쌍은 한국 날짜 하루 1개만 적립한다.

## 10. Place·지도·산책

- 외부 Provider 결과는 내부 Place DTO로 정규화한다.
- 검색 결과는 `(provider, providerPlaceId)`로 `places`를 upsert한 뒤 내부 `placeId`를 발급해 반환한다.
- Board, Meeting, Walk가 동일한 내부 `placeId`를 사용한다.
- 검색 원본·쿼터·장애를 Provider adapter 뒤에 격리한다.
- 산책 위치는 batch로 업로드하며 중복 sequence를 멱등 처리한다.
- 위치·경로 보존 기간과 인기 경로 공개 기준은 `D-11` 결정 대기다.
