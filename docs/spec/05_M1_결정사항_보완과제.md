## 1. 요약

### 확정 결정

1. 한 User가 등록할 수 있는 Pet은 같은 `owner_user_id`를 가진 행 중 `deleted_at IS NULL`인 Pet을 기준으로 최대 5마리다.
2. 회원탈퇴 기능 전체를 M1 완료 범위에서 제외하고 POST-M1으로 이동한다.
3. Pet은 `status = DELETED ↔ deleted_at IS NOT NULL`의 양방향 불변조건을 따른다.
4. 첫 Pet 생성과 Active Pet 자동 지정은 각각 독립적으로 Commit되는 두 트랜잭션으로 실행한다.

### 즉시 보완

- 비로그인 `GET /neighborhoods`, 활성 동네 필터와 Security GET 공개는 PR #6에서 반영됐다.
- 일반 USER에게 M1 범용 `/media/**` 업로드 흐름이 노출되지 않도록 제한한다.
- 최신 M1 문서 8개를 Git에서 재현 가능한 정본으로 만들고 잘못된 경로·파일명을 바로잡는다.
- 상태 전이와 충돌하는 API Markdown Example을 Schema 변경과 구분하여 고친다.
- Auth Refresh Rotation, Logout 전체 폐기와 Controller·Service 회귀 테스트는 PR #6에서 반영됐다.
- Pet 생성 트랜잭션에서 `firstPetCandidate`를 확정해 Active 지정 단계로 전달하고, L1 사용자의 수동 Active Pet 선택 복구 흐름까지 구현한다.
- Pet 한도 조회·동시 생성 제어, Pet 삭제 상태 불변조건, 첫 Pet 생성 후 Active 자동 지정의 분리 트랜잭션을 확정 계약대로 구현한다.
- 네 가지 확정 결정을 기준으로 Pet Core 구현을 시작할 수 있다.

### 추가 확정 결정

5. 관리자 신고 상세는 신고자·피신고자 User와 양쪽 Pet, room, 전체 messages를 담는 전용 Evidence DTO를 사용한다.
6. HTTP Status는 기본 `400/403/404/409`로 단순화하고 필요한 endpoint만 별도 Status를 추가한다. `PET_LIMIT_EXCEEDED`는 `409`다.
7. M1 범용 미디어 정책 오류는 `MEDIA_PURPOSE_FORBIDDEN`으로 통합한다.
8. 등록정보 Provider는 M1에서 동기 처리하고 canonical 등록번호가 없으면 `REJECTED`로 종결한다.
9. 카드 버튼은 최근 24시간 내 사용자 TEXT 2개 이상일 때 활성화하고, 서버는 0~1개에도 `200 + INSUFFICIENT_CONTEXT` 빈 폼을 반환한다.
10. 정적 `04_M1_OpenAPI.yaml`만 REST 계약 정본으로 사용하며 런타임 문서 대조를 필수 Gate로 두지 않는다.
11. 회원탈퇴는 새 WBS ID 없이 POST-M1 이동을 기록하고 과거 ID가 발견될 때만 `MOVED`로 복원한다.

### 2026-07-27 교차검토 확정

1. 물리 스키마 정본은 Flyway Migration이며 통합 SQL은 M1 목표 구조 참고용이다.
2. 동기 등록정보 Attempt는 완료 후 최종 상태만 저장하고 `PENDING`을 저장하지 않는다.
3. User와 Pet PublicTag는 별도 Namespace다.
4. Pet PublicTag는 nickname 앞 25개 Unicode code point와 `#XXXX`로 만든다.
5. Pet PublicTag Unique 충돌은 새 트랜잭션에서 최대 5회 재시도한다.
6. Pet nickname은 trim 후 1자 이상이다.
7. 내 Pet 목록은 Active Pet 우선, 나머지는 `createdAt ASC, petId ASC`다.
8. M1 Pet `profileUrl`은 null이며 클라이언트가 기본 이미지를 표시한다.
9. M1 Pet 생성은 Idempotency-Key를 제공하지 않으며 timeout·5xx 뒤 목록을 먼저 재조회한다.
10. `RETRY_REQUIRED`는 예상 가능한 일시적 Active 지정 실패에만 사용한다.
11. 소유권 실패는 기본 403이며 존재 은닉이 필요한 endpoint만 OpenAPI에 404를 명시한다.
12. WIP 커밋은 원격 Push 전 로컬에서만 사용한다.
13. 별도 HTTP Status는 정적 OpenAPI부터 코드·테스트까지 같은 PR에서 변경한다.
14. API 상세 오류 표에는 endpoint·Status별 대표 실제 ErrorCode를 기록한다.
15. WBS M1-002·003은 교차검토 완료 전 `부분완료`로 표시한다. `M1-013A`는 기존 보존 ID다.

### POST-M1 이동

`DELETE /me`, 탈퇴 Service, Cleanup, 토큰 폐기, 관계 정리, 비동기 재시도, 개인정보 익명화·파기, 탈퇴 화면을 M1에서 구현하지 않는다. DB의 `WITHDRAWN`, `withdrawn_at` 등 미래 확장 구조는 즉시 제거 대상으로 보지 않는다.

## 2. 확정 결정 1 — Pet 최대 5마리

### 최종 결정

한 User의 Pet 한도는 다음 조건으로 계산한다.

```text
같은 owner_user_id를 가진 Pet 중
deleted_at IS NULL인 Pet의 수
```

- `ACTIVE` Pet은 포함한다.
- `SUSPENDED` Pet도 `deleted_at IS NULL`이면 포함한다.
- 양방향 삭제 불변조건에 따라 `deleted_at IS NOT NULL`인 Pet은 반드시 `status=DELETED`이며 한도에서 제외한다.
- 삭제 Pet의 이력 행은 보존할 수 있으며 신규 등록 한도에는 포함하지 않는다.
- 한도는 애플리케이션의 단순 사전 조회만으로 보장하지 않는다. 같은 User의 동시 생성 요청을 직렬화하는 잠금 또는 동등한 동시성 제어가 필요하다.

Pet 한도 계산과 함께 적용할 `status=DELETED`와 `deleted_at`의 양방향 불변조건은 확정 결정 3에서 정한다. 회원탈퇴 시 Pet의 최종 상태와 삭제된 Pet 복구·관리자 정지 해제 정책은 이번 M1 결정으로 새로 만들지 않는다.

### 결정 이유

- `01_M1_통합_ERD.md`의 **PETS**는 “사용자당 활성 Pet 최대 5마리”라고 표현하지만 `SUSPENDED`와 삭제 이력의 포함 여부를 구분하지 않는다.
- 삭제 이력 보존과 현재 등록 한도를 동시에 운영하려면 집계 조건이 재현 가능해야 한다.
- 이번 팀 결정으로 집계 기준을 `deleted_at IS NULL` 하나로 고정해 관리자 정지와 삭제 후 재등록의 결과를 명확히 한다.

### 계산 예시

| ACTIVE | SUSPENDED | DELETED (`deleted_at IS NOT NULL`) | 한도 계산 결과 | 신규 등록 |
|---:|---:|---:|---:|---|
| 4 | 1 | 0 | 5 | 거절, `PET_LIMIT_EXCEEDED` |
| 3 | 1 | 1 | 4 | 허용 가능 |
| 5 | 0 | 3 | 5 | 거절, `PET_LIMIT_EXCEEDED` |
| 0 | 5 | 2 | 5 | 거절, `PET_LIMIT_EXCEEDED` |

### 영향 범위

- **M1 범위:** Pet 직접 등록, 관리자 정지 Pet, Pet 삭제 후 신규 등록의 한도 판정
- **영향 문서:** `00_최신_제품정책.md` **3. Pet 삭제와 인증**, `01_M1_통합_ERD.md` **3. 사용자와 Pet / PETS**, `01_M1_통합_ERD.sql`의 `pets`, `02_M1_API_계약.md` **Pet / 공통 오류 코드**, `04_M1_API_명세.md` **3.4 Pet**, `04_M1_OpenAPI.yaml`의 `/pets` 및 Pet 오류 응답, `04_M1_마일스톤_WBS.md`의 Pet 작업·Gate
- **영향 코드:** 현재 브랜치에는 Pet Controller, Service, DTO, Entity, Repository 구현이 없다. 새 Pet 생성 Service, `deleted_at IS NULL` 수 조회 Repository Query, 동시성 제어 경계에 반영해야 한다.
- **오류 계약:** 다섯 마리 이상이면 `409 PET_LIMIT_EXCEEDED`를 일관되게 반환한다.

### 구현 기준

1. Repository 집계는 `owner_user_id`와 `deleted_at IS NULL`만을 한도 조건으로 사용한다. `status=ACTIVE`만 세는 쿼리를 만들지 않는다.
2. Pet 생성 Service는 owner User 기준으로 동시 요청을 직렬화한 생성 트랜잭션에서 생성 전 미삭제 Pet 수를 조회한다.
3. 생성 전 수가 0이면 `firstPetCandidate=true`, 1 이상이면 `firstPetCandidate=false`를 확정한다.
4. 확정한 생성 전 수로 최대 5마리 한도를 검사하고 Pet을 저장한다.
5. 생성된 Pet과 `firstPetCandidate` 내부 결과를 함께 반환하고 Commit한다. 외부 API에는 기존 `activeAssignmentStatus`만 유지한다.
6. 관리자 정지로 `SUSPENDED`가 되어도 삭제되지 않았다면 가용 슬롯이 늘지 않는다.
7. 삭제가 확정되어 `status=DELETED`, `deleted_at IS NOT NULL`이 된 뒤에는 가용 슬롯이 하나 늘어난다.
8. 기술 방식은 User 행 비관적 잠금, advisory lock, 직렬화 가능한 동등 방식 중 구현 환경에 맞게 선택할 수 있으나 단순 `count → insert`만으로 끝내면 안 된다.

구현 선택 범위: Pet 생성 트랜잭션에서 owner User를 기준으로 한도 판정과 생성을 하나의 임계 구역으로 만든다. 구체적인 잠금 또는 동등한 직렬화 방식은 구현 리뷰에서 선택하되 동시 요청에서도 최대 5마리 계약을 반드시 지킨다.

### 테스트 기준

- PostgreSQL 통합 테스트로 0→1, 4→5, 5→거절 경계를 검증한다.
- `ACTIVE 4 + SUSPENDED 1`이면 생성이 거절되는지 검증한다.
- 삭제 Pet 행이 `status=DELETED`, `deleted_at IS NOT NULL` 조합으로 남아도 한도에서 제외되는지 검증한다.
- Pet 삭제 후 신규 등록이 가능한지 검증한다.
- 같은 User의 동시 생성 요청으로 최종 미삭제 Pet 수가 5를 초과하지 않는지 검증한다.
- 동시 생성 요청에서 생성 전 수가 0인 하나의 요청만 `firstPetCandidate=true`가 되는지 검증한다.
- 경쟁 요청 중 거절된 요청이 `PET_LIMIT_EXCEEDED`로 수렴하는지 검증한다.

### 변경이 필요한 문서

- “활성 Pet 최대 5마리”를 “같은 owner의 `deleted_at IS NULL` Pet 최대 5마리”로 교체한다.
- `SUSPENDED` 포함, `status=DELETED`·`deleted_at IS NOT NULL` 제외, 삭제 후 재등록 가능을 명시한다.
- Pet 생성 전 수로 `firstPetCandidate`를 확정하고 Active 지정 단계에 전달한다는 계약과 동시성 테스트를 추가한다.
- `PET_LIMIT_EXCEEDED`의 endpoint·`409 Conflict`·응답 Schema를 정적 OpenAPI와 동기화한다.

## 3. 확정 결정 2 — 회원탈퇴 POST-M1

### 최종 결정

회원탈퇴는 M1에서 구현하지 않고 POST-M1에서 별도 설계한다.

이는 최신 원본의 기존 M1 표현을 변경한 확정 결정이다. 작성 당시 `00_최신_제품정책.md` **9. 회원탈퇴**, `01_M1_통합_ERD.md` **USERS**, `04_M1_API_명세.md` **3.3 Me / DELETE /me**, `04_M1_OpenAPI.yaml`의 `/me` DELETE가 M1 구현 대상으로 읽혔으나 현재 정본에서는 POST-M1로 격리했다.

### M1에서 제거되는 범위

- `DELETE /me`
- User 탈퇴 Service
- 탈퇴 Cleanup
- 탈퇴 시 Refresh Token 폐기 흐름
- 탈퇴 시 Pet 비활성화 또는 최종 상태 변경
- 탈퇴 시 Friendship 제거와 FriendRequest 정리
- 탈퇴 비동기 작업과 실패 재시도
- 개인정보 익명화·파기
- 탈퇴 관련 사용자 화면
- 회원탈퇴를 대상으로 한 M1 완료 조건, Gate, WBS 작업

### 유지 가능한 기반 구조

- DB와 Entity의 `WITHDRAWN`, `withdrawn_at` 같은 미래 확장용 구조는 이번 결정만으로 제거하지 않는다.
- 현재 기반 코드나 적용된 Flyway Migration에 미래 탈퇴 상태가 있어도 즉시 되돌리지 않는다.
- 다만 미래 구조의 존재를 M1 회원탈퇴 구현 완료 증거로 사용하지 않는다.

## 4. 확정 결정 3 — Pet 삭제 상태 불변조건

### 최종 결정

Pet의 삭제 상태와 삭제시각은 다음 양방향 불변조건을 반드시 만족한다.

```text
status = DELETED ↔ deleted_at IS NOT NULL
```

`DELETED`이면 반드시 `deleted_at`이 있어야 하며, `deleted_at`이 있으면 반드시 `DELETED`여야 한다. `ACTIVE`와 `SUSPENDED`는 삭제되지 않은 상태이므로 `deleted_at`이 항상 `NULL`이다.

### 상태별 허용 조합

| status | deleted_at | 허용 여부 |
|---|---|---|
| ACTIVE | NULL | 허용 |
| SUSPENDED | NULL | 허용 |
| DELETED | NOT NULL | 허용 |
| ACTIVE | NOT NULL | 금지 |
| SUSPENDED | NOT NULL | 금지 |
| DELETED | NULL | 금지 |

### 영향 범위

- **M1 범위:** 일반 Pet 삭제, 관리자 정지, Pet 최대 5마리 집계, 삭제 후 신규 등록
- **영향 문서:** `00_최신_제품정책.md` **3. Pet 삭제와 인증**, `01_M1_통합_ERD.md` **3. 사용자와 Pet / PETS**, `01_M1_통합_ERD.sql`의 `pets`, `03_M1_상태전이.md`에 추가할 Pet 상태 전이, `04_M1_API_명세.md` **3.4 Pet**, `04_M1_OpenAPI.yaml`의 Pet Schema, `04_M1_마일스톤_WBS.md`의 Pet 완료 조건
- **영향 코드:** 현재 브랜치에는 Pet 도메인 구현과 Pet Flyway Migration이 없다. 새 Pet Entity·Service·Repository와 신규 Pet Migration에 처음부터 반영한다.

### 구현 기준

1. 일반 Pet 삭제는 `status=DELETED`와 `deleted_at=현재 시각`을 같은 트랜잭션에서 함께 변경한다.
2. 관리자 정지는 `status=SUSPENDED`, `deleted_at=NULL`로 처리한다.
3. SUSPENDED Pet은 삭제되지 않은 Pet이므로 최대 5마리 한도에 포함한다.
4. DELETED Pet은 `deleted_at IS NOT NULL`이므로 최대 5마리 한도에서 제외한다.
5. 삭제된 Pet을 ACTIVE 또는 SUSPENDED로 되돌리는 복구 정책은 이번 결정에서 새로 만들지 않는다.
6. 회원탈퇴 시 Pet의 최종 상태는 POST-M1에서 별도로 결정한다.

### DB 불변조건

기존 공유 Flyway Migration은 수정하지 않는다. 현재 Pet Migration이 없으므로 신규 Pet Migration에 다음 의미의 CHECK를 처음부터 포함한다.

```sql
CHECK (
    (status = 'DELETED' AND deleted_at IS NOT NULL)
    OR
    (status IN ('ACTIVE', 'SUSPENDED') AND deleted_at IS NULL)
)
```

실제 제약 이름은 프로젝트 DB 네이밍 규칙에 맞춰 신규 Migration 변경 계획에서 정한다. CHECK만으로 Service의 관계 정리·권한·트랜잭션 책임이 대체되는 것은 아니다.

### 테스트 기준

- ACTIVE + `deleted_at=NULL` 허용
- SUSPENDED + `deleted_at=NULL` 허용
- DELETED + `deleted_at NOT NULL` 허용
- ACTIVE/SUSPENDED + `deleted_at NOT NULL` 거절
- DELETED + `deleted_at=NULL` 거절
- 삭제 Service가 `status`와 `deleted_at`을 같은 트랜잭션에서 함께 변경
- 삭제 후 `deleted_at IS NULL` 집계 슬롯이 하나 증가
- 관리자 정지는 `deleted_at=NULL`을 유지하므로 슬롯을 증가시키지 않음

### 변경이 필요한 문서

- Pet 상태별 `deleted_at` 허용 조합과 일반 삭제 전이를 명시한다.
- 관리자 정지와 일반 삭제를 서로 다른 상태 전이로 구분한다.
- 신규 Pet Migration과 PostgreSQL 통합 테스트를 WBS 완료 조건에 추가한다.
- 회원탈퇴 시 Pet 최종 상태와 삭제 Pet 복구 정책은 POST-M1 또는 별도 결정으로 남긴다.

## 5. 확정 결정 4 — 첫 Pet 생성과 Active 지정 트랜잭션 분리

### 최종 결정

첫 Pet 생성과 Active Pet 자동 지정은 각각 독립적으로 Commit되는 두 트랜잭션으로 분리한다. Pet 생성 성공과 Active 지정 성공은 하나의 성공 여부로 합치지 않는다.

### 1단계 — Pet 생성 트랜잭션

1. owner User를 기준으로 동시 등록 요청을 직렬화하거나 동등한 동시성 제어를 적용한다.
2. 생성 전 같은 owner의 `deleted_at IS NULL` Pet 수를 조회한다.
3. 생성 전 수가 0이면 `firstPetCandidate=true`, 1 이상이면 `firstPetCandidate=false`를 확정한다.
4. 확정한 생성 전 수로 최대 5마리 한도를 검사한다.
5. Pet을 저장하고, 생성된 Pet과 `firstPetCandidate` 내부 결과를 함께 반환한 뒤 Commit한다.
6. Pet 생성 자체가 실패하면 `firstPetCandidate` 결과와 관계없이 Active 지정 단계를 실행하지 않는다.

```text
생성 전 미삭제 Pet 수 = 0
→ firstPetCandidate = true

생성 전 미삭제 Pet 수 >= 1
→ firstPetCandidate = false
```

### 2단계 — Active Pet 자동 지정 트랜잭션

Pet 생성 Commit 이후 별도 트랜잭션에서 Active Pet 자동 지정을 시도한다. Active 지정 단계는 Pet 수를 다시 세어 첫 Pet 여부를 추정하지 않으며, 생성 트랜잭션이 전달한 `firstPetCandidate`만 사용한다.

1. `firstPetCandidate=true`인 생성 결과에만 Active 자동 지정 트랜잭션을 실행한다.
2. `firstPetCandidate=false`이면 Active 자동 지정을 시도하지 않고 `NOT_APPLICABLE`을 반환한다.
3. 후보인 경우 User의 현재 `active_pet_id`를 확인한다.
4. Active Pet이 없고 조건을 충족하면 생성된 Pet을 Active Pet으로 지정한다.
5. 후보였으나 이미 `active_pet_id`가 있으면 새 Active 값을 덮어쓰지 않고 `NOT_APPLICABLE`로 처리한다.
6. lock timeout·deadlock 등 예상 가능한 일시 실패는 이미 Commit된 Pet 생성을
   Rollback하지 않고 `RETRY_REQUIRED`로 처리한다.
7. DB 연결 장애·무결성 오류·코딩 오류는 `RETRY_REQUIRED`로 숨기지 않는다.

동시 생성 요청도 owner User 기준으로 생성 요청이 직렬화되므로, 생성 전 수가 0인 첫 번째 요청 하나만 `firstPetCandidate=true`가 될 수 있어야 한다.

실제 구현은 Spring 자기 호출로 인해 두 트랜잭션이 합쳐지지 않도록 별도 Service Bean, `TransactionTemplate` 또는 동등하게 독립 Commit이 보장되는 방식을 사용한다. 특정 기술 하나를 강제하지 않지만 두 단계의 독립 Commit은 고정 계약이다.

### API 결과

| 상황 | `activeAssignmentStatus` |
|---|---|
| `firstPetCandidate=true`이고 Active 지정 성공 | `ASSIGNED` |
| `firstPetCandidate=true`이고 lock timeout·deadlock 등 예상 가능한 일시 실패 | `RETRY_REQUIRED` |
| `firstPetCandidate=false` 또는 후보 단계에서 이미 Active Pet 존재 | `NOT_APPLICABLE` |

- `RETRY_REQUIRED`여도 Pet 생성은 성공했으며 Pet 행은 저장되어 있다.
- `POST /pets`는 `RETRY_REQUIRED`에도 `201 Created`와 생성된 Pet 정보를 반환한다.
- `RETRY_REQUIRED`를 일반 Pet 생성 실패로 처리하지 않는다.
- 클라이언트는 `RETRY_REQUIRED`이면 Pet 프로필 또는 Active Pet 선택 화면으로 이동시킨다.
- 사용자는 기존 Active Pet 변경 API로 생성된 Pet을 직접 Active Pet으로 선택할 수 있다.
- M1은 Idempotency-Key를 제공하지 않는다. timeout·5xx 응답 뒤에는
  `GET /pets/me`로 생성 여부를 먼저 확인하고 POST를 무작정 재시도하지 않는다.
- 현재 최신 계약의 `ASSIGNED`, `RETRY_REQUIRED`, `NOT_APPLICABLE`을 유지하며 `SUCCESS` 같은 새 enum은 추가하지 않는다.
- `firstPetCandidate`는 내부 생성 결과 또는 Service 간 전달값이며, 외부 응답에 새 필드로 노출하지 않는다.

### L1 사용자의 수동 Active Pet 선택 복구

`RETRY_REQUIRED` 이후에도 Active Pet이 없는 L1 사용자는 기존 Active Pet 변경 API(또는 Active Pet 선택 API)를 호출할 수 있다. 정확한 URL과 HTTP Status는 최신 원본 계약을 유지하며, 이 문서는 새 endpoint를 만들지 않는다.

- API는 인증된 User가 호출하며 현재 `active_pet_id`가 `NULL`이어도 호출할 수 있다.
- 이 API의 선행 조건으로 `ACTIVE_PET_REQUIRED`를 사용하지 않는다.
- 대상 Pet은 요청 User가 소유하고, `status=ACTIVE`, `deleted_at IS NULL`이어야 한다.
- `SUSPENDED` 또는 `DELETED` Pet은 Active Pet으로 선택할 수 없다.
- 성공하면 `users.active_pet_id`를 대상 Pet ID로 변경한다.

```text
POST /pets
→ Pet 생성 성공
→ lock timeout·deadlock 등 예상 가능한 일시적 Active 지정 실패
→ 201 Created + RETRY_REQUIRED
→ Pet 프로필 또는 Active Pet 선택 화면
→ Active Pet 선택 API 호출
→ 대상 Pet 소유권·ACTIVE 상태·deleted_at IS NULL 검증
→ active_pet_id 변경
```

### 구현 시 구체화할 사항

다음은 확정된 두 트랜잭션 계약을 바꾸지 않는 범위에서 구현 명세로 구체화한다.

- Active 지정 단계에서 로깅·관찰할 예외
- 예상하지 못한 DB 장애·무결성 오류·코딩 오류는 `RETRY_REQUIRED`로 변환하지 않는다.
- API 응답 전 네트워크 단절로 인한 클라이언트 중복 등록 가능성

`권장 해석`(구현 명세에서 구체화할 세부 규칙)은 다음과 같다.

- 후보 결과를 전달받은 뒤 다른 요청이 먼저 Active Pet을 지정해 현재 Active Pet이 이미 존재하면 `NOT_APPLICABLE`이다.
- Active Pet이 없는 상태에서 lock timeout·deadlock 등 예상 가능한 일시 실패가
  발생하면 `RETRY_REQUIRED`다.
- DB 연결 장애·무결성 오류·코딩 오류는 정상 오류 흐름으로 처리한다.
- Pet 생성 트랜잭션 자체가 실패하면 일반 생성 실패이며 `RETRY_REQUIRED`가 아니다.

이 해석의 예외 처리·관찰 범위는 구현 명세에서 구체화하되 새로운 제품 상태나 enum을 만들지 않는다.

### 영향 범위

- **영향 문서:** `00_최신_제품정책.md` **11. M1 API 기본값**, `01_M1_통합_ERD.md` **USERS / PETS**, `02_M1_API_계약.md` **Pet**, `04_M1_API_명세.md` **POST /pets / PetCreateResult**, `04_M1_OpenAPI.yaml`의 `createPet`·`PetCreateResult`, `04_M1_마일스톤_WBS.md`의 Pet 작업·Gate
- **영향 코드:** 현재 Pet 도메인은 미구현이다. Pet 생성 트랜잭션 경계와 Active 지정 트랜잭션 경계를 별도 구성요소 또는 독립 트랜잭션 실행 단위로 구현해야 한다.
- **클라이언트:** `201 Created` 안의 `activeAssignmentStatus`로 후속 화면을 분기하며, `RETRY_REQUIRED`이면 L1 사용자도 기존 Active Pet 변경 API로 수동 복구한다.

### 테스트 기준

- 첫 Pet 생성 후 Active 지정 성공 → `ASSIGNED`
- 생성 전 미삭제 Pet 수가 1 이상이면 `firstPetCandidate=false` 및 Active 지정 단계 미실행 → `NOT_APPLICABLE`
- `firstPetCandidate=true`인 Pet 생성 Commit 후 예상 가능한 일시적 Active 지정 실패 → Pet 행 유지 + `RETRY_REQUIRED`
- `RETRY_REQUIRED` 응답이 `201 Created`와 생성된 Pet 정보를 포함
- Active Pet이 없는 L1 사용자가 `ACTIVE`·미삭제인 본인 Pet을 직접 Active Pet으로 선택 가능
- Active 선택 API가 `ACTIVE_PET_REQUIRED`를 선행 조건으로 사용하지 않음
- 타인 Pet, SUSPENDED Pet, DELETED 또는 `deleted_at IS NOT NULL` Pet 선택 거절
- 동시 첫 Pet 생성에서 하나의 요청만 `firstPetCandidate=true`이고 Pet 한도와 Active Pet 단일성 유지
- 예상 가능한 일시적 Active 지정 실패가 Pet 생성 트랜잭션을 Rollback하지 않음
- Pet 생성 자체 실패 시 Active 지정 단계 미실행

### 변경이 필요한 문서

- 첫 Pet 생성 Commit과 Active 지정 Commit이 분리된다는 점을 명시한다.
- 생성 전 Pet 수에 따른 `firstPetCandidate` 확정·내부 전달과 `ASSIGNED`, `RETRY_REQUIRED`, `NOT_APPLICABLE` 조건을 동기화한다.
- 프런트의 `RETRY_REQUIRED` 후속 화면, L1 수동 Active 선택과 대상 Pet 검증 흐름을 완료 조건에 넣는다.
- 분리 트랜잭션과 장애 시 Pet 행 유지 여부를 PostgreSQL 통합 테스트 기준에 추가한다.

### 7.2 오류 코드와 HTTP Status

**현재 확인된 계약**

- `02_M1_API_계약.md` **공통 오류 코드**, endpoint별 응답표, `04_M1_OpenAPI.yaml`, `ErrorCode` Schema, `src/main/java/itda/common/constants/ErrorCode.java`가 완전히 동기화되어 있지 않다.
- 작성 당시 요약 문서는 `SETLOG_UPLOAD_NOT_AVAILABLE`, 코드는 `MEDIA_PURPOSE_FORBIDDEN`을 사용해 충돌했다.
- 현재 `ErrorCode.java`의 `SETLOG_SELF_REACTION_FORBIDDEN`은 400이지만 해당 OpenAPI operation의 응답표에 필요한 400이 빠진 곳이 있다.
- Markdown 오류 표는 endpoint·Status별 대표 실제 ErrorCode 하나를 제공하며,
  전체 목록은 정적 OpenAPI와 endpoint 오류 매트릭스를 따른다.

**최종 결정**

- 기본 Status는 `400` 형식·검증, `403` 권한·행위 금지, `404` 조회 불가, `409` 중복·한도·상태 충돌이다.
- 기본 네 값으로 표현하기 어려운 endpoint에만 별도 Status를 명시한다.
- `POST /setlogs/{setlogId}/greetings`의 Pet당 하루 10명 초과는 endpoint별 예외인 `429 Too Many Requests`다.
- `PET_LIMIT_EXCEEDED`는 `409`다.
- 미디어 정책 오류는 `MEDIA_PURPOSE_FORBIDDEN`으로 통합하고 `SETLOG_UPLOAD_NOT_AVAILABLE`은 사용하지 않는다.

**필수 산출물**

다음 열을 가진 전체 매트릭스를 API 계약 정본으로 만든다.

```text
endpoint × 실패 상황 × HTTP Status × ErrorCode × 응답 Schema × 담당 도메인
```

`ErrorCode.java`, 정적 OpenAPI operation responses, Markdown 응답표, Controller 테스트를 같은 변경 단위로 맞춘다.

### 7.3 등록정보 Attempt

**현재 확인된 계약**

- `01_M1_통합_ERD.sql`의 M1 상태는 `SUCCEEDED`, `REJECTED`, `FAILED`, `EXPIRED`, `CONSUMED`다.
- `04_M1_API_명세.md` **3.5 PetVerification**과 OpenAPI의 외부 응답 상태는 최종 결과 중심이다. 내부·외부 상태가 다르다는 사실만으로 충돌은 아니다.
- `00_최신_제품정책.md` **10. 외부 확인**은 canonical 등록번호가 없으면 인증 배지를 발급하지 않으며 직접 등록은 허용한다.
- 보호자 이름·생년월일은 Provider 요청에만 사용하고 저장하지 않는다. 저장소 코딩 규칙상 로그에도 남기면 안 된다.
- 현재 코드에는 Attempt 또는 Provider Adapter 구현이 없다.

**최종 결정**

- M1 Provider는 동기 처리한다.
- Provider 완료 후 Attempt를 `SUCCEEDED`, `REJECTED`, `FAILED` 중 최종 상태로
  저장한다. M1은 `PENDING`을 DB에 저장하지 않는다.
- canonical 등록번호가 없거나 정보가 불일치하면 `REJECTED`로 종결한다.
- `SUCCEEDED`에서만 consume할 수 있고 중복 consume은 `409`다.
- 보호자 이름·생년월일은 `writeOnly`, 비영속이며 로그에 남기지 않는다.

**선택지와 영향**

| 선택지 | 영향 |
|---|---|
| 동기 Provider·최종 응답 | API가 단순하지만 timeout/failure 및 재시도 계약 필요 |
| 비동기 Provider·조회 API 추가 | `PENDING`이 자연스럽지만 현재 endpoint 계약과 WBS 변경 필요 |
| 내부 상태는 상세히 유지하고 외부 상태를 명시 매핑 | DB 운영과 API 단순화를 함께 얻지만 매핑표가 필수 |

Provider timeout·장애는 `FAILED`로 구분하며 직접 Pet 등록 경로는 항상 유지한다.

### 7.4 약속 카드 메시지 2개 조건

**현재 확인된 계약**

- `04_M1_마일스톤_WBS.md` **7. M1 Gate**는 메시지 2개 이상인 방에서 버튼이 활성화된다고 한다.
- `04_M1_API_명세.md` **POST /chat/rooms/{roomId}/card-drafts**는 최근 30개·24시간 문맥과 fallback을 설명한다.
- `CardDraft.fallbackReason`에는 `INSUFFICIENT_CONTEXT`가 있다.
- 현재 코드에는 MeetingCard 구현이 없다.

**최종 결정**

- 프런트는 최근 24시간 내 사용자 `TEXT` 메시지가 2개 이상일 때 버튼을 활성화한다.
- `CARD`, `SYSTEM`은 개수와 AI 입력에서 제외한다.
- 서버는 0~1개 직접 호출도 거절하지 않고 `200`, 빈 폼, `fallbackReason=INSUFFICIENT_CONTEXT`를 반환한다.
- AI에는 최근 24시간 내 사용자 TEXT를 최대 30개만 전달한다.

**선택지와 영향**

| 선택지 | 영향 |
|---|---|
| UI Gate만 적용, 서버는 fallback 반환 | API 복원력이 높지만 클라이언트와 Gate 문구를 구분해야 함 |
| 서버도 2개 미만 호출 거절 | 계약이 엄격하지만 별도 ErrorCode·HTTP Status가 필요 |
| 0·1개도 `INSUFFICIENT_CONTEXT` 빈 폼 반환 | fallback-first와 맞지만 reason 의미를 확정해야 함 |

AI timeout·model error도 기존 fallback reason으로 200 빈 폼을 반환한다.

### 7.5 정적 OpenAPI 운영 방식

**현재 확인된 계약**

- `04_M1_OpenAPI.yaml`은 목표 M1 계약을 기술한다.
- `src/main/java/itda/common/config/SwaggerConfig.java`의 `openApi`와 런타임 `/v3/api-docs`는 현재 구현된 Controller를 반영한다.
- 구현 중 두 문서가 다른 것은 자연스럽지만, 프런트가 어느 쪽을 소비하는지와 완료 시 대조 방식은 정해져 있지 않다.

**검토했던 선택지**

| 선택지 | 영향 |
|---|---|
| 정적 OpenAPI를 개발 중 프런트 정본으로 지정 | 병렬 개발이 쉽지만 구현 완료 시 drift 검사가 필요 |
| 런타임 `/v3/api-docs`를 정본으로 지정 | 실제 구현과 맞지만 미구현 API의 선행 계약 제공이 어렵다 |
| 정적 계약을 목표, 런타임을 구현 증거로 분리 | 역할이 명확하지만 CI 비교·예외 승인 절차가 필요 |

**최종 결정:** Git에 추적된 정적 `04_M1_OpenAPI.yaml`만 REST 계약 정본으로 사용한다. 런타임 `/v3/api-docs`는 현재 구현 관찰용이며 정본 또는 필수 CI 비교 Gate로 사용하지 않는다.
