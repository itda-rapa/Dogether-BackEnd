# 같이놀개 M1 상태 전이

## Pet

| 현재 | 사건 | 다음 | `deleted_at` | 부수효과 |
|---|---|---|---|---|
| 없음 | 직접 등록 Commit | ACTIVE | NULL | 내부 `firstPetCandidate` 확정 |
| ACTIVE | 관리자 정지 | SUSPENDED | NULL | Active Pet이면 `users.active_pet_id=NULL` |
| ACTIVE | 일반 삭제 | DELETED | 현재 시각 | Friendship 삭제·양방향 PENDING 요청 취소 |
| SUSPENDED | 일반 삭제 | DELETED | 현재 시각 | Friendship 삭제·양방향 PENDING 요청 취소 |

`status = DELETED ↔ deleted_at IS NOT NULL`은 양방향 불변조건이다.
`ACTIVE`, `SUSPENDED`는 `deleted_at=NULL`이고 최대 5마리 한도에 포함한다.
삭제 Pet 복구는 M1에 없다.

## First Pet Active Assignment

| 생성 결과 | Active 지정 사건 | 결과 | Pet 생성 Commit |
|---|---|---|---|
| `firstPetCandidate=true` | Active 지정 성공 | ASSIGNED | 유지 |
| `firstPetCandidate=true` | 자동 지정 트랜잭션의 비관적 잠금 실패 | RETRY_REQUIRED | 유지 |
| `firstPetCandidate=false` 또는 기존 Active 존재 | 지정 미실행 | NOT_APPLICABLE | 유지 |

Pet 생성과 Active 지정은 독립 트랜잭션이다. Active 지정 단계는 Pet 수를 다시 세어
첫 Pet 여부를 추정하지 않고 생성 단계의 내부 후보값만 사용한다.
`NOT_APPLICABLE`은 `firstPetCandidate=false`이거나 다른 요청이 먼저 Active Pet을
지정해 자동 지정 시점에 기존 `active_pet_id`가 존재하는 경우에만 사용한다.
생성 Pet 행 누락, owner User 불일치, 예상하지 못한 `SUSPENDED`·`DELETED` 상태,
`deleted_at` 불변조건 위반 등 데이터·코드 불변조건 위반은 `RETRY_REQUIRED`나
`NOT_APPLICABLE`로 변환하지 않는다. 자동 Active 지정 트랜잭션을 Rollback하고,
원인이 식별되면 원인에 맞는 일반 오류 흐름으로 처리하며 예상하지 못한 시스템·코드
오류는 기존 내부 오류 흐름과 오류 로그 정책을 따른다. `BusinessException`은 기존
비즈니스 오류 흐름을 따른다. 자동 지정의 비관적 잠금 실패를 `RETRY_REQUIRED`로
변환할 때는 `userId`, `petId`와 Stack Trace를 포함한 경고 로그를 남긴다.
선행 Pet 생성 트랜잭션이 이미 Commit됐다면 후속 Active 지정이 일반 오류로 실패해도
생성된 Pet은 유지된다. `RETRY_REQUIRED`는 생성 Commit 이후 자동 지정에서 발생한
`PessimisticLockingFailureException`에만 사용한다. Pet 생성 트랜잭션 자체의 잠금
실패는 Pet을 Commit하지 않고 `409 CONCURRENT_UPDATE_CONFLICT`로 처리한다.

## Registration Attempt

| 현재 | 사건 | 다음 |
|---|---|---|
| 없음 | 동기 Provider 완료·canonical 등록번호 확인 | SUCCEEDED |
| 없음 | 동기 Provider 완료·정보 불일치 또는 canonical 번호 없음 | REJECTED |
| 없음 | timeout·Provider 장애 | FAILED |
| SUCCEEDED | Pet에 적용 | CONSUMED |
| SUCCEEDED | 유효기간 경과 | EXPIRED |

consume은 `SUCCEEDED`에서만 허용하며 중복 consume은 `409` 상태 충돌이다.
M1은 처리 중간 `PENDING`을 DB에 저장하지 않는다.

## Greeting

| 현재 | 사건 | 다음 | 부수효과 |
|---|---|---|---|
| 없음 | 최초 인사 | SENT | DIRECT 방·Participant·최초 TEXT 생성 |
| SENT | 상대 최초 답변 | RESPONDED | 이후 자유 대화 |
| SENT | 24시간 무답 | EXPIRED | 신고 없으면 방·Participant·메시지 물리 삭제 |

`EXPIRED`는 종결 상태이며 재인사는 허용하지 않는다.

## ChatRoom

| 현재 | 사건 | 다음 |
|---|---|---|
| ACTIVE | 답변한 비친구 방 30일 무활동 | ARCHIVED |
| ARCHIVED | 정상 메시지 전송 | ACTIVE |

## FriendRequest

| 현재 | 사건 | 다음 |
|---|---|---|
| 없음 | 요청 | PENDING |
| PENDING | 상대가 반대 방향 요청 | ACCEPTED |
| PENDING | 수락 | ACCEPTED |
| PENDING | 거절 | REJECTED |
| PENDING | 발신 취소 | CANCELED |
| PENDING | 7일 경과 | EXPIRED |

`ACCEPTED` 전이 시 Friendship 한 행을 생성한다.
반대 방향의 유효한 PENDING 요청이 있으면 새 요청을 만들지 않고 기존 요청을
`ACCEPTED`로 전이한다. 이때 기존 `requestId`, 요청 방향, `requestedAt`,
`expiresAt`을 유지하고 `respondedAt`만 수락 시각으로 기록한다.

`expiresAt <= now`인 PENDING은 `EXPIRED`로 전이하고 `respondedAt`은 `null`로
유지한다. 같은 Pet pair로 새 요청을 만들 때는 EXPIRED 전이를 먼저 반영한 뒤
새 PENDING을 저장한다.

명시적 수락과 거절은 현재 Active Pet이 수신 Pet일 때만, 취소는 현재 Active
Pet이 발신 Pet일 때만 허용한다. 권한이 없는 requestId는 존재를 숨겨 404로
응답한다. 수락·거절·취소 중 만료를 발견하면 `EXPIRED` 전이를 별도 쓰기
트랜잭션에서 정상 커밋한 뒤 외부에는 `FRIEND_REQUEST_NOT_PENDING`을 반환한다.

`ACCEPTED`, `REJECTED`, `CANCELED`는 `respondedAt`에 전이 시각을 기록한다.
거절·취소는 관계 종료 작업이므로 Block 여부와 상대 User·Pet 상태에 관계없이
행위자의 Active Pet 조건만 만족하면 처리하며 Friendship과 Chat을 만들지 않는다.

Friendship 생성 시 양쪽 Pet의 현재 친구 수를 검사하며, Pet당 최대 50개까지
허용한다. 일반 PENDING 생성에는 친구 수 제한을 적용하지 않는다.

## Friendship

Friendship은 상태 enum을 두지 않는다. 정렬 Pet pair 행의 존재가 친구 관계다.
삭제 시 기존 ChatRoom과 Message는 유지한다.

## MeetingCard

| 현재 | 사건 | 다음 |
|---|---|---|
| 없음 | 필수값 확인 후 확정 | OPEN |
| OPEN | 참여 Pet 중 한쪽이 취소 | CANCELED |

M1에서는 수정·복구가 없다.

## Report

| 현재 | 사건 | 다음 |
|---|---|---|
| 없음 | 신고 접수 | OPEN |
| OPEN | 관리자 경고 | ACTIONED |
| OPEN | 관리자 기각 | NO_ACTION |

신고 접수만으로 차단하지 않는다.
`ACTIONED`, `NO_ACTION`은 종결 상태이며 추가 조치를 허용하지 않는다.

## UserBlock

M1에서 생성만 가능하며 해제 상태 전이는 없다. 행 존재가 차단 상태다.
