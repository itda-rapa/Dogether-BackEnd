# Dogether 백엔드 코딩 컨벤션

이 문서는 Dogether 백엔드 코드 작성과 리뷰의 기준이다. 현재 프로젝트의
Java 25, Spring Boot 4, PostgreSQL, Flyway, JWT, S3 구조를 기준으로 한다.

## 1. 언어·표기

| 대상 | 규칙 | 예 |
|---|---|---|
| 클래스·record·enum 타입 | PascalCase | `MediaAsset`, `SignupRequest` |
| 변수·메서드 | camelCase | `mediaAssetId`, `issueTokens` |
| 상수·enum 값·오류 코드 | UPPER_SNAKE_CASE | `MEDIA_EXPIRED` |
| 패키지 | 영문 소문자 | `itda.media.service` |
| DB 테이블·컬럼·인덱스 | snake_case | `refresh_tokens`, `expires_at` |
| API 경로 | 소문자·kebab-case, 리소스는 복수 명사 | `/meeting-cards` |
| 에러 메시지·주석·PR·커밋 | 한국어 | `[FIX] 만료 토큰 처리 수정` |

영문 기술 용어는 팀 문서에서 사용 중인 표기를 따른다. 같은 개념을 Pet, pet,
반려견처럼 임의로 섞지 않는다.

`/auth`, `/admin`처럼 리소스보다 기능 그룹을 나타내는 경로는 단수형을 허용한다.

## 2. 패키지 구조

도메인은 다음 구조를 기본으로 한다.

```text
itda.<domain>/
├─ controller/
├─ service/
├─ repository/
├─ domain/
└─ dto/
```

필요할 때만 `policy`, `mapper`, `event` 등의 하위 패키지를 추가한다. 빈 패키지를
유지하기 위한 placeholder 파일은 만들지 않는다.

공통 코드는 `itda.common`에 두되, 두 개 이상의 도메인에서 실제로 재사용할 때만
공통화한다. 한 도메인의 편의를 위해 공통 패키지를 오염시키지 않는다.

## 3. 클래스 이름

| 종류 | 형식 | 예 |
|---|---|---|
| Entity | 단수 명사 | `User`, `MediaAsset` |
| Repository | `<Entity>Repository` | `UserRepository` |
| Service | `<Domain>Service` | `AuthService` |
| 보조 Service | 역할이 드러나는 이름 | `MediaStatusService` |
| Controller | `<Domain>Controller` | `AuthController` |
| Request DTO | `<Action><Entity>Request` | `PetCreateRequest` |
| Response DTO | `<Entity>Response` | `MediaAssetResponse` |
| Properties | `<Purpose>Properties` | `JwtProperties` |
| Config | `<Purpose>Config` | `SecurityConfig` |
| Filter | `<Purpose>Filter` | `JwtFilter` |

서비스 메서드 동사:

- 단건 조회: `get`, `find`, `require`
- 목록 조회: `list`, `search`
- 생성: `create`, `register`, `issue`
- 변경: `update`, `change`, `mark`, `revoke`
- 삭제: `delete`, `requestDeletion`
- 검증: `validate`, `check`

이름만 보고 부수효과를 알 수 있어야 한다. 조회 메서드에서 상태를 변경하지 않는다.

## 4. Controller와 API 응답

Controller의 역할:

- 요청 DTO 검증
- 인증 사용자 전달
- Service 호출
- HTTP 상태와 공통 응답 생성

Controller에 비즈니스 규칙이나 Repository 호출을 넣지 않는다.

성공 응답은 다음 중 하나를 사용한다.

```java
ApiResponse<T>
ResponseEntity<ApiResponse<T>>
ResponseEntity<Void>
```

Entity를 API 응답으로 직접 반환하지 않는다. 응답 DTO의 `from` 정적 팩토리를
우선 사용한다.

```java
return ApiResponse.ok(
        MediaAssetResponse.from(mediaAsset, viewUrl),
        "미디어 자산이 조회되었습니다."
);
```

생성은 201, 정상 조회·변경은 200, 응답 본문 없는 삭제·로그아웃은 204 또는 비동기
삭제 요청이면 202를 사용한다.

## 5. 입력 검증

- 요청 DTO는 `record`를 우선 사용한다.
- Controller에서 `@Valid`를 적용한다.
- `@NotNull`, `@NotBlank`, `@Size`, `@Positive` 등 Bean Validation을 사용한다.
- DTO 형식 검증과 도메인 상태 검증을 구분한다.
- 소유권, 계정 상태, Active Pet, 차단 관계 같은 규칙은 Service에서 검증한다.
- 클라이언트가 보낸 role, userId, ownerId를 권한 판단의 정본으로 신뢰하지 않는다.

## 6. 예외와 오류 코드

예상 가능한 비즈니스 실패는 다음 형태로 표현한다.

```java
throw new BusinessException(ErrorCode.MEDIA_EXPIRED);
```

규칙:

- 오류 코드는 `ErrorCode` enum에 등록한다.
- 이름은 영문 UPPER_SNAKE_CASE를 사용한다.
- 같은 실패 원인에 새 오류 코드를 중복 생성하지 않는다.
- 인증 실패는 401, 권한·소유권 실패는 403을 구분한다.
- 존재하지 않는 자원은 404, 상태 충돌은 409를 우선한다.
- 예상하지 못한 예외만 `INTERNAL_ERROR` 500으로 변환한다.
- `IllegalArgumentException`으로 비즈니스 실패를 표현하지 않는다.
- 예외를 잡고 무시해야 한다면 재시도·보상·관측 방법을 주석과 문서에 남긴다.

외부 시스템의 내부 메시지, SQL, 스택트레이스, 토큰 값을 API 응답에 노출하지 않는다.

## 7. Service와 트랜잭션

- 트랜잭션 경계는 Service 메서드에 둔다.
- 읽기 전용 메서드는 `@Transactional(readOnly = true)`를 사용한다.
- DB 상태 변경은 하나의 명확한 트랜잭션에서 처리한다.
- `REQUIRES_NEW`, 비관적 잠금, `noRollbackFor`를 사용하면 이유와 실패 시나리오를
  테스트로 남긴다.
- 예외를 던진 뒤에도 반드시 커밋되어야 하는 폐기·만료 상태는 별도 경계를 사용한다.
- PostgreSQL 제약 위반이 발생한 트랜잭션 안에서 다시 쿼리하지 않는다.
- 외부 API 호출을 DB 트랜잭션 안에서 수행해야 한다면 잠금 시간과 재시도 영향을
  검토한다.
- Controller에서 `@Transactional`을 사용하지 않는다.

동시성 규칙은 애플리케이션의 사전 조회만으로 보장하지 않는다. Unique 제약,
조건부 UPDATE, 잠금과 함께 설계한다.

## 8. Entity와 JPA

- 기본 생성자는 `@NoArgsConstructor(access = AccessLevel.PROTECTED)`로 제한한다.
- Entity에 public setter와 Lombok `@Data`를 사용하지 않는다.
- 생성은 의미가 드러나는 정적 팩토리를 우선한다.
- 상태 변경은 Entity 메서드로 표현한다.
- 연관관계는 LAZY를 기본으로 한다.
- 양방향 연관관계는 꼭 필요한 경우에만 사용한다.
- 목록 조회의 N+1 가능성을 확인한다.
- API DTO에 Entity를 그대로 전달하지 않는다.
- 시간은 `Instant`와 PostgreSQL `TIMESTAMPTZ`를 사용하고 서버 기준 UTC로 저장한다.
- ID는 현재 정본인 `BIGINT IDENTITY`와 Java `Long`을 사용한다.
- 낙관적 충돌 감지가 필요한 Aggregate에는 `@Version`을 사용한다.

예:

```java
public static MediaAsset pending(
        User owner,
        MediaPurpose purpose,
        String objectKey,
        String contentType,
        long sizeBytes,
        Instant expiresAt
) {
    return new MediaAsset(
            owner,
            purpose,
            objectKey,
            contentType,
            sizeBytes,
            expiresAt
    );
}
```

## 9. Repository와 PostgreSQL

- Repository는 Spring Data JPA 인터페이스를 기본으로 한다.
- 쿼리 이름이 길어지거나 의미가 불명확하면 `@Query`를 사용한다.
- 수정 쿼리는 `@Modifying`과 트랜잭션 경계를 명시한다.
- PostgreSQL의 partial index, expression index, generated column, CHECK 제약을
  H2 테스트만으로 검증하지 않는다.
- 이메일 대소문자 Unique처럼 DB가 최종 보장해야 하는 규칙은 migration에 작성한다.
- 페이지네이션은 계약에 따라 cursor 또는 offset을 선택하며 임의로 혼용하지 않는다.

## 10. Flyway

- 한 번 공유되거나 원격에 올라간 migration은 수정하지 않는다.
- 변경은 다음 버전 migration으로 추가한다.
- migration 파일명:

```text
V<번호>__<영문_snake_case_설명>.sql
```

- 개발 전용 seed는 운영 migration과 분리한다.
- migration 번호를 만들기 전에 최신 `dev`와 다른 작업자의 번호를 확인한다.
- FK, Unique, CHECK, index 이름을 명시한다.
- PostgreSQL에서 `postgresTest`를 실행해 migration 전체 적용과 Hibernate 정합성을
  검증한다.

## 11. 보안

- 비밀번호 원문과 Refresh Token 원문을 DB에 저장하지 않는다.
- principal과 로그에 비밀번호 해시를 넣지 않는다.
- Access Token의 role만 믿지 않고 필요한 경우 현재 사용자 상태를 DB에서 확인한다.
- `/admin/**`는 ADMIN 이상 권한을 명시한다.
- 소유권 검사는 ID 존재 확인과 별도로 수행한다.
- `.env`, AWS Key, JWT Secret, 관리자 비밀번호를 커밋하지 않는다.
- 운영 AWS 자격증명은 IAM Role 또는 표준 자격증명 체인을 사용한다.
- 이메일, 생년월일, 토큰, 채팅 원문 등 개인정보·민감정보를 로그에 남기지 않는다.

## 12. 환경설정

- 설정값은 `@ConfigurationProperties`로 묶는다.
- 필수값은 애플리케이션 시작 시 Bean Validation으로 검증한다.
- 신규 환경변수는 `.env.example`과 README를 함께 수정한다.
- local·test·prod 차이는 profile 파일로 분리한다.
- 운영 Swagger는 비활성화한다.
- 코드에 환경별 URL이나 자격증명을 하드코딩하지 않는다.

## 13. S3와 미디어

- 파일 본문은 Presigned URL로 클라이언트가 S3에 직접 업로드한다.
- 서버는 목적, MIME, 크기, 소유권과 업로드 완료 상태를 검증한다.
- object key는 서버에서 생성한다.
- 클라이언트 파일명을 object key 정본으로 사용하지 않는다.
- S3Client와 S3Presigner의 region, endpoint, path-style 설정을 일치시킨다.
- 삭제 실패와 미완료 업로드는 재시도 또는 Lifecycle 정책을 가진다.

## 14. 로깅

- `log.info`: 중요한 비즈니스 상태 전이와 운영 이벤트
- `log.warn`: 예측 가능한 비정상 흐름 중 운영 확인이 필요한 경우
- `log.error`: 예상하지 못한 서버 오류와 스택트레이스
- `log.debug`: 개발용 상세 정보

검증 실패를 전부 warn으로 남겨 로그를 오염시키지 않는다. `System.out.println`을
사용하지 않는다.

## 15. 테스트

### 빠른 테스트

```powershell
.\gradlew.bat test
```

- 도메인 규칙 단위 테스트
- Service 실패 경로
- Security 접근 권한
- Spring Context

### PostgreSQL 통합 테스트

```powershell
.\gradlew.bat postgresTest
```

- Flyway 전체 적용
- PostgreSQL 전용 문법·제약·인덱스
- 트랜잭션 커밋·롤백
- 동시성·잠금

테스트 이름은 어떤 조건에서 무엇을 기대하는지 드러내야 한다.

```java
void signupRetriesAfterPublicTagUniqueCollision()
void expiredUploadPersistsExpiredStatusBeforeReturningGone()
void adminPathRejectsNormalUser()
```

given/when/then 구조를 사용하되, 형식보다 읽기 쉬운 실패 시나리오 표현을 우선한다.
외부 연동은 단위 테스트에서 대역을 사용하고 실제 계약 검증은 별도 통합 테스트로
구분한다.

## 16. 포맷과 코드 품질

- 들여쓰기는 공백 4칸을 사용한다.
- 한 줄은 120자 이내를 권장한다.
- 파일 끝에는 newline 하나를 둔다.
- import wildcard를 사용하지 않는다.
- 생성자 주입을 사용하고 필드 주입을 금지한다.
- 사용하지 않는 import, 클래스, 설정, 오류 코드를 남기지 않는다.
- 의미 없는 주석보다 이름과 구조로 의도를 표현한다.
- TODO를 PR에 방치하지 않고 GitHub Issue로 관리한다.
- 대규모 포맷 변경은 기능 PR과 분리한다.

현재 자동 포매터가 없으므로 IntelliJ 기본 Java 포맷을 사용한다. Spotless 같은
자동 포맷터를 도입하면 build 설정과 이 문서를 같은 PR에서 수정한다.

## 17. 리뷰 체크리스트

- Controller가 Repository를 직접 호출하지 않는가?
- Entity가 API에 직접 노출되지 않는가?
- 권한과 소유권을 모두 확인하는가?
- 예외가 올바른 HTTP 상태와 ErrorCode로 변환되는가?
- 실패 후 DB 상태가 의도대로 커밋 또는 롤백되는가?
- 동시성 규칙을 DB 제약 없이 사전 조회만으로 처리하지 않았는가?
- 새 migration과 기존 Entity가 일치하는가?
- PostgreSQL 전용 기능에 `postgresTest`가 있는가?
- 민감정보가 로그·응답·Git diff에 없는가?
- API·ERD·enum·상태 전이 문서가 동기화됐는가?
