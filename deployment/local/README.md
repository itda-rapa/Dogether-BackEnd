# Open Chat Implementation Guide

## 로컬 경로 Heatmap 빈도 데이터

저장 완료된 실제 경로의 선형을 복제하여 `인기 경로` 테마의 고빈도/저빈도 차이를 확인할 수 있다.
운영 Flyway에는 포함되지 않으며 로컬 PostgreSQL에만 명시적으로 적용한다.

```powershell
Get-Content .\deployment\local\seed-route-heatmap.sql -Raw |
  docker exec -i dogether-postgres psql -U postgres -d dogether
```

스크립트는 `environment_info.mockDataset=route-heatmap-frequency-v1`으로 생성 행을 표시한다.
반복 실행하면 기존 표시 행을 먼저 삭제하므로 데이터가 계속 증가하지 않는다. 원본 저장 경로가
5개 이상이면 각 경로에 160/60/18/5/1개의 복제본을 만들어 극명한 빈도 분포를 제공한다.

이 문서는 Dogether 백엔드와 `dogether-consumer` 프로젝트를 기준으로 오픈채팅방 기능을 완성하기 위해 보완해야 할 항목을 정리한다.

현재 구현은 Kafka를 통해 메시지를 전달하고 consumer가 STOMP topic으로 브로드캐스트하는 흐름은 갖추고 있다. 다만 오픈채팅방을 운영 가능한 수준으로 제공하려면 방 도메인, 인증/인가, 메시지 저장-발행 일관성, 조회 권한, consumer ack 처리를 추가로 보완해야 한다.

## 1. 오픈채팅방 도메인 보완

현재 `chat_rooms`는 DIRECT 채팅 중심 구조다. `RoomType.GROUP`은 존재하지만 오픈채팅방에 필요한 메타데이터가 부족하다.

필요한 정보:

- 방 제목
- 방 설명
- 방장 pet 또는 user
- 공개 여부
- 최대 참여 인원
- 오픈채팅 origin

예시 migration:

```sql
ALTER TABLE chat_rooms
ADD COLUMN title VARCHAR(100),
ADD COLUMN description VARCHAR(500),
ADD COLUMN owner_pet_id BIGINT,
ADD COLUMN max_participants INT,
ADD COLUMN is_public BOOLEAN NOT NULL DEFAULT TRUE;

ALTER TABLE chat_rooms
DROP CONSTRAINT ck_chat_room_origin;

ALTER TABLE chat_rooms
ADD CONSTRAINT ck_chat_room_origin
CHECK (origin IN ('GREETING', 'FRIEND', 'OPEN_CHAT'));
```

`RoomOrigin`에도 `OPEN_CHAT`을 추가한다.

```java
public enum RoomOrigin {
    GREETING,
    FRIEND,
    OPEN_CHAT
}
```

오픈채팅방 생성 API는 DIRECT 채팅 생성과 분리하는 것이 좋다.

```java
@PostMapping("/open")
public ResponseEntity<ApiResponse<ChatRoomResponse>> createOpenRoom(
        @AuthenticationPrincipal CurrentUser currentUser,
        @Valid @RequestBody OpenChatRoomCreateRequest request
) {
    ChatRoomResponse response = chatRoomService.createOpenRoom(currentUser.id(), request);
    return ResponseEntity.ok(ApiResponse.ok(response, "오픈채팅방 생성 성공"));
}
```

중요한 원칙:

- `ownerPetId`를 request에서 그대로 믿지 않는다.
- `currentUser.id()` 기준으로 active pet을 서버에서 조회한다.
- 방장, 참여자, 메시지 발신자는 서버가 결정한다.


## 3. 메시지 저장과 Kafka 발행 일관성

현재 흐름은 Kafka 발행 후 DB 저장에 가깝다. 이 경우 Kafka 메시지는 나갔지만 DB 저장이 실패하거나, DB는 저장됐지만 consumer 전달이 실패하는 문제가 생길 수 있다.

최소 보완안은 DB 저장 후 Kafka 발행이다.

```java
@Transactional
public ChatMessageResponse sendMessage(long userId, long roomId, ChatMessageCreateRequest request) {
    ActivePetContext actor = activePetQueryService.requireActivePet(userId);

    validateParticipant(roomId, actor.petId());

    ChatRoom room = chatRoomRepository.findByIdOrThrow(roomId);
    ChatMessage saved = chatMessageRepository.save(
            ChatMessage.fromPet(room, request.body(), actor.petId())
    );

    kafkaTemplate.send("chat-message-topic", roomId.toString(), toEvent(saved));

    return ChatMessageResponse.from(saved);
}
```

운영 안정성을 높이려면 outbox 패턴을 적용한다.

```text
1. chat_messages 저장
2. chat_message_outbox 저장
3. 트랜잭션 commit
4. 별도 publisher가 outbox 미발행 이벤트를 Kafka로 전송
5. 성공 시 outbox 상태를 SENT로 변경
6. 실패 시 재시도
```

outbox 테이블 예시:

```sql
CREATE TABLE chat_message_outbox (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    message_id BIGINT NOT NULL,
    room_id BIGINT NOT NULL,
    payload TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    retry_count INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    sent_at TIMESTAMPTZ
);
```

## 4. REST 메시지 조회 권한 검증

메시지 조회 API는 `roomId`만으로 조회하면 안 된다. 반드시 `currentUser` 기준으로 active pet을 찾고, 해당 pet이 방 참가자인지 확인해야 한다.

Controller 예시:

```java
@GetMapping("/{roomId}/messages")
public ResponseEntity<ApiResponse<Page<ChatMessageResponse>>> getRoomMessages(
        @AuthenticationPrincipal CurrentUser currentUser,
        @PathVariable Long roomId,
        Paging paging
) {
    Page<ChatMessageResponse> response = chatQueryService.getMessages(
            currentUser.id(),
            roomId,
            paging.toPageable()
    );

    return ResponseEntity.ok(ApiResponse.ok(response, "메시지 조회 성공"));
}
```

Service 예시:

```java
public Page<ChatMessageResponse> getMessages(long userId, long roomId, Pageable pageable) {
    ActivePetContext actor = activePetQueryService.requireActivePet(userId);

    if (!participantRepository.existsByRoomIdAndPetIdAndLeftAtIsNull(roomId, actor.petId())) {
        throw new BusinessException(ErrorCode.NOT_PARTICIPANT_OF_CHAT_ROOM);
    }

    return chatMessageRepository.getMessages(roomId, pageable);
}
```

오픈채팅방이 공개 조회를 지원하더라도 실시간 채팅 메시지는 입장 후 조회만 허용하는 편이 안전하다.

## 5. Consumer 중복 메시지 ack 처리

consumer는 Redis로 중복 처리 여부를 확인한다. 현재 중복 메시지일 때 바로 return하면 수동 ack 모드에서 메시지가 다시 소비될 수 있다.

수정 전:

```java
if (!Boolean.TRUE.equals(isFirstProcessing)) return;
```

수정 후:

```java
if (!Boolean.TRUE.equals(isFirstProcessing)) {
    ack.acknowledge();
    return;
}
```

DLQ 발행 실패 시에는 ack하지 않는 것이 맞다. 다만 같은 메시지가 계속 재시도될 수 있으므로 retry, backoff, max attempt 정책을 추가하는 것이 좋다.

## 최소 보완 적용 순서

1. `joinToRoom()` 권한 검증 버그 수정
2. `send()` 참가자 검증 조건 수정
3. 오픈채팅방 생성 API 추가
4. 오픈채팅방 입장/퇴장 API 추가
5. REST 메시지 조회 API에 `currentUser` 기반 참가자 검증 추가
6. WebSocket `CONNECT`, `SUBSCRIBE`, `SEND` 인증/인가 인터셉터 추가
7. 메시지 저장 후 Kafka 발행으로 순서 변경
8. consumer 중복 메시지 ack 처리 수정
9. 운영 안정성이 필요하면 outbox 패턴 도입

## 핵심 원칙

클라이언트가 보내는 `petId`, `senderPetId`, `roomId`는 신뢰하지 않는다. 서버는 항상 `currentUser` 기준으로 active pet과 room participant 여부를 다시 계산해야 한다.

오픈채팅에서 최소한 서버가 책임져야 하는 것은 다음과 같다.

- 누가 방을 만들 수 있는가
- 누가 방에 입장할 수 있는가
- 누가 방을 구독할 수 있는가
- 누가 메시지를 보낼 수 있는가
- 저장된 메시지를 누가 조회할 수 있는가
- DB 저장과 Kafka 발행이 서로 어긋났을 때 어떻게 복구할 것인가
